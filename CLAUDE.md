## Инфраструктура: какой хост актуальный

**По умолчанию работай на этой машине.** Исключение — старый прод, см. ниже.

| | адрес | статус |
|---|---|---|
| текущий prod | `31.128.43.113` (hostname `nazicimzxh`) | **живой, это здесь** |
| бывший prod | `45.130.212.62` (hostname `oladaymbzh`) | **временно поднят, ssh работает** |

Эта машина изначально была dev-сервером и в июле 2026 стала продом.

**29 июля 2026 старый прод восстановили** — вопреки тому, что здесь было
написано раньше. Он живой, крон бэкапов на нём отрабатывает, ssh с этой
машины пускает по ключу без пароля. Оттуда забраны дампы за 28 и 29 июля
(`/root/backup/directus_*.sql`, `n8n_*.sql`), лежат в
`/root/restore-old-prod/old-prod-dumps/` в gzip.

Поднят он **на ограниченное время**. Если с него ещё что-то нужно — забирать
сейчас, а не потом. Быстрее всего `rsync -z` (plain SQL жмётся ~17×):

```
rsync -avz --partial -e 'ssh -o BatchMode=yes' \
  root@45.130.212.62:/root/backup/ФАЙЛ /root/restore-old-prod/
```

Когда его снова отключат — эту таблицу поправить обратно.

Осторожно с ssh-алиасами: в конфиге пользователя алиас с именем `prod` в
разное время указывал на разные машины. Не полагайся на имя алиаса — сверяйся
с IP. На самой этой машине `~/.ssh/config` отсутствует, алиасов нет вообще.

### Зеркало старого прода: `/root/sync-old-prod.sh`

Старый прод `45.130.212.62` — **не архив, а живой второй прод**: обслуживает
`smm.omemo.tech` (DNS этого домена смотрит туда, а не сюда), там работают
тестировщики и заводят баги в Jira. Данные двух серверов расходятся в обе
стороны.

Скрипт зеркалит его БД сюда, односторонне, в отдельную базу **`old_prod_sync`**.
Живая `directus` не участвует и не может пострадать. Прогон ~17 минут (основное
время — снятие дампа на старом сервере), снимок ~235 МБ.

Крон — `/etc/cron.d/sync-old-prod`, каждые два часа в `:15`, лог
`/var/log/sync-old-prod.log`. **Поставлен только 29.07.2026**: до этого дня в
CLAUDE.md было написано «запуск по крону раз в два часа», но крона не было
нигде (проверено: `crontab -l` root, `/etc/crontab`, `/etc/cron.d/`, syslog) —
зеркало жило только ручными запусками. Обёрнут в `flock -n`: прогон длиннее,
чем кажется, и наложение двух запусков снесло бы `old_prod_sync_tmp` под
работающим. **Снять этот файл после переноса DNS** `smm.omemo.tech` и финального
снимка.

Устройство: `pg_dump -Fc` выполняется в контейнере старого сервера, результат
идёт потоком через ssh — на старом проде не меняются ни крон, ни конфиг, ни
диск. Восстановление сперва во временную базу, проверка (≥40 таблиц), и только
потом замена прошлого зеркала. Оборванный дамп или отключение старого сервера
посреди прогона оставляют предыдущее зеркало целым. `DROP DATABASE` ограничен
префиксом `old_prod_sync*`.

Последние снимки лежат в `/root/restore-old-prod/sync/` (скрипт хранит восемь;
на 29.07.2026 их два — прогонов было столько) — это архив на момент, когда
старый сервер отключат насовсем.

Логическую репликацию Postgres не используем сознательно: она потребовала бы
`wal_level=logical` и перезапуска боевого Postgres на временно поднятой машине.

### Бакет Beget S3 отдаёт объекты анонимно

Бакет `6e679636ae90-ridiculous-seth` (эндпоинт `s3.ru1.storage.beget.cloud`,
регион `ru-central-1`, креды `BEGET_S3_*` в `/root/.env`) обслуживает медиа

Следствия:

- В корне бакета с 23.06.2025 **лежит** `.env` с боевыми секретами, включая

  `/root/restore-old-prod/old-server-config/LEAKED-bucket-root.env` (600).

- Утёкший `DIRECTUS_PASSWORD` совпадает с текущим `POSTGRES_PASSWORD`
  контейнера `root-postgres-1`.
- Смягчает: 5432 и 8055 наружу не опубликованы, только внутри docker-сети.
  Но Directus торчит в интернет через Traefik, а токен статический.

**Дампы БД в этот бакет заливать нельзя** ни под каким префиксом. Для
бэкапов нужен отдельный приватный бакет, дампы шифровать перед загрузкой.

Статус на 29.07.2026: ротация токена и паролей **не выполнена** — требует

## Jira

Проект ведётся в Jira Server/DC: `https://jira.nutrientplaner.ru`.

**Доступ.** Креды лежат на хосте в `/root/.config/jira/env` (права 600, в
репозиторий не коммитятся). Подключение:

```bash
set -a; . /root/.config/jira/env; set +a
curl -sS -H "Authorization: Bearer $JIRA_TOKEN" "$JIRA_URL/rest/api/2/myself"
```

Важно: это Jira **Server/DC**, а не Cloud. Авторизация только Personal Access
Token через `Authorization: Bearer`. Схема `Basic email:token` из Jira Cloud тут
не работает — не тратить на неё время.

**Проекты.**

| ключ | что | кто заводит |
|---|---|---|
| `SM` | smm manager — баги от тестировщиков | тестировщики |
| `AI` | «AI Маркетинг», мёртв с февраля 2025 (31 задача, все от 2025) | никто |

**Типы задач** в SM: `Задача`, `Подзадача`, `История`, `Ошибка`, `Epic`.
**Переходы** (id для `POST /rest/api/2/issue/{key}/transitions`):
`11` → Сделать, `21` → В работе, `31` → Готово, `41` → Протестировано.

**Права аккаунта `signmark`:** `CREATE_ISSUE`, `ADMINISTER_PROJECTS`,
`BULK_CHANGE` есть; глобального `ADMINISTER` нет — **создать новый проект
нельзя**. Отсюда открытый вопрос ниже.

**Открытый вопрос:** владелец хочет отдельный бэклог с префиксом `DEV-`, чтобы
инженерные задачи не мешались с багами тестировщиков. Создать проект некому:
глобального админа нет ни у владельца, ни у бота. Варианты: (1) кто-то с правами
админа заводит проект `DEV`; (2) переименовать мёртвый `AI` в `DEV` — это
поменяет ключи у всех существующих `AI-*`, поэтому требует явного разрешения
владельца; (3) вести в `SM` типом `Задача` под отдельным эпиком — префикс
останется `SM-`.

### Рабочий процесс с тикетами

- Баг закрывается только после выката на прод и проверки. В комментарии — что
  было, в чём причина, каким коммитом, как проверено.
- Не закрывать непроверенное. Если подтвердить не удалось — оставить открытым и
  написать, каких данных не хватает.
- «Работает по замыслу» — законный исход, но с объяснением и предложением
  завести отдельную задачу на изменение поведения.

### Сборка образа при втором исполнителе в дереве

Docker берёт контекст из **рабочего дерева**, а не из HEAD. Пока в `/root/smm`
параллельно работает кто-то ещё, `docker compose build smm` унесёт в прод его
незакоммиченные правки. В этом раунде так и было — сборка шла из чистого
worktree:

```bash
git worktree add /root/smm-build-clean origin/main
docker build -t root-smm -f /root/smm-build-clean/Dockerfile /root/smm-build-clean
docker compose -f /root/docker-compose.yml up -d --no-build smm
```

`--no-build` обязателен: без него compose пересоберёт образ из `/root/smm` и
вернёт ровно ту проблему.

### Новое в окружении и схеме

- **`TRENDS_WEBHOOK_SECRET`** в `/root/.env` — секрет шести публичных колбэков
  трендов. Без него они отвечают 503 (fail-closed), а не работают без проверки.
  Резервная копия `.env` до правки: `/root/.env.bak-20260729-trends`.
- **`promo_reservations.payment_attempt_at`** (timestamp, nullable) — маркер
  «по этой брони уже пошли в платёжную систему». На нём держится денежный
  инвариант: он отличает бронь, брошенную ДО создания платежа (её можно
  освободить), от той, где платёж создан, а привязка сорвалась (слот держим).
  Сбой его записи **прерывает оплату** намеренно — делать запись best-effort
  нельзя, вернётся та самая неразличимость, ради которой он и заведён.
