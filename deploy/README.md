# deploy/ — эталон боевого стека, запускать отсюда нечего

## Что здесь лежит

`prod-stack.reference.yml` — побайтовая копия боевого `/root/docker-compose.yml`.
Одиннадцать сервисов: traefik, n8n, postgres, pgadmin, directus-uploads-init, directus,
smm, video-app, smmniap, videoapp, proxy.

**Канон по выкатке — [`docs/DEPLOYMENT.md`](../docs/DEPLOYMENT.md).** Этот каталог его не
заменяет и не описывает, как выкатывать: он существует только чтобы у боевого файла была
история изменений.

## Зачем понадобилось (AI-71)

Боевой compose описывает всю топологию продакшена и до 17.08.2026 не лежал ни в одном
репозитории. Вместо истории рядом с ним копились копии вида `docker-compose.yml.bak-*`.
Правка боевой топологии не проходила ревью, не имела diff и откатывалась сравнением
резервных копий по датам. При этом сломанный файл блокирует не только свой сервис:
`scripts/deploy-smm.sh` читает этот же compose, то есть встаёт и выкатка `smm`.

## Почему имя файла именно такое

Прежняя редакция этого README запрещала класть в каталог compose-файлы, и запрет был
правильный. Причина: `docker compose` без `-f` подхватывает файл из текущего каталога,
а параллельный стек с теми же `container_name` и портами 80/443 уронит прод.

Запрет снят не целиком, а ровно в той части, которая его вызывала. `docker compose`
автоматически подхватывает только четыре имени: `compose.yaml`, `compose.yml`,
`docker-compose.yaml`, `docker-compose.yml`. Имя `prod-stack.reference.yml` в этот список
не входит, поэтому случайный запуск из каталога невозможен физически, а не по договорённости.

**Правило остаётся: файл с автоподхватываемым именем в этот каталог не класть.**

## Секреты

Их здесь нет и быть не должно. Проверено построчно перед первым коммитом 17.08.2026:
132 присваивания окружения, из них 25 чистых подстановок `${VAR}`, одна подстановка со
значением по умолчанию, 7 шаблонов и 99 литералов — все безобидные (метки traefik, CORS,
номера портов, сроки жизни токенов, имена хостов). Пароли приходят из `/root/.env`,
которого в репозитории нет и не будет.

При каждой правке этого файла проверять то же самое заново. Дешёвый способ убедиться, что
не добавилось литерального значения: посмотреть, что все чувствительные ключи справа от
знака равенства содержат `${...}`, а не текст.

## Как этот файл попадает на прод

Никак не попадает сам. Здесь эталон, на хосте — обычный файл, и это сделано намеренно.

Симлинк с `/root/docker-compose.yml` в репозиторий делать нельзя: тогда любая выкатка
меняет боевую топологию в момент обновления рабочей копии, и неудачный мерж ломает прод
не когда его заметили, а сразу.

Порядок правки:

1. Правишь `deploy/prod-stack.reference.yml` в ветке, обычным порядком — гейт, ревью, мерж.
2. После вливки переносишь на хост осознанным шагом, с копией предыдущего состояния:

   ```
   cp /root/docker-compose.yml /root/docker-compose.yml.bak-$(date +%Y%m%d-%H%M%S)
   cp <рабочая-копия>/deploy/prod-stack.reference.yml /root/docker-compose.yml
   docker compose -f /root/docker-compose.yml up -d <только затронутый сервис>
   ```

3. Поднимать весь стек целиком без нужды не надо — перезапускается только тот сервис,
   которого касалась правка.

## Проверка расхождения

Эталон и боевой файл разъезжаются молча, если правку внесли на хосте мимо репозитория.
Проверяется одной командой на боевом хосте:

```
diff /root/docker-compose.yml <рабочая-копия>/deploy/prod-stack.reference.yml
```

Пусто — расхождения нет. Есть вывод — кто-то правил файл на хосте напрямую; правку надо
перенести в репозиторий, а не затирать.
