# План перевода логов на пригодный к разбору вид

Цель: в проде в лог попадает только то, по чему можно принять решение, каждая
строка машиночитаема и связана с запросом/пользователем/кампанией, а Sentry
ставится последним — на уже готовый фундамент.

Порядок этапов важен: пока уровни врут, любой сборщик логов будет собирать враньё.

---

## 0. Что сломано сейчас (замеры, не ощущения)

**Каналов логирования — два, ведут себя противоположно.**

| Точка входа | Что делает в production |
|---|---|
| `log(msg, src, 'info')` = `logMessage` | **выкидывает** |
| `log(msg, src, 'error')` | выкидывает, если в тексте нет одной из 12 фраз (`КРИТИЧЕСКАЯ ОШИБКА`, `Сервис недоступен`, …) |
| `log.info(msg)` = `info()` | **печатает всегда** |
| `log.warn(msg)` = `warn()` | печатает всегда |
| `log.error(msg, err)` = `error()` | выкидывает, если нет критической фразы |
| `systemError(msg)` | печатает **только в development** |
| `console.log/error` напрямую | печатает всегда, мимо любых правил |

То есть `log(x, s, 'info')` молчит, а `log.info(x)` — кричит. Автор строки не может
предсказать, увидит ли он её. Отдельно: `error()` в development **молча съедает**
любую axios-ошибку со статусом 401/403/429 ([logger.ts:246](../server/utils/logger.ts:246)) —
ровно тот класс, который мы сегодня искали.

**Объём вызовов** (server/, без тестов): `log(` — 3706, `console.log` — 1271,
`console.error` — 715, `console.warn` — 164, `logMessage(` — 8.
Вывод: переписывать все 5800 точек нельзя, менять надо транспорт под ними.

**`LOG_LEVEL` объявлен и не используется.** `envConfig.logLevel` считается в
[environment-detector.ts:39](../server/utils/environment-detector.ts:39), а в самом
логгере не читается ни разу — уровень задаётся только жёсткими `if`.

**Нет корреляции.** Access-лог — одна строка `console.log('[HTTP] GET /path')`
([index.ts:263](../server/index.ts:263)): без статуса, без длительности, без id
запроса. Связать ошибку в сервисе с вызовом, который её породил, нечем.

**56 молчаливых `catch {}`** (плюс 10 вида `catch (_)`). Каждый — потенциально
сломанная функция, о которой никто не узнает; сегодняшние 403 жили именно там.

**Docker пишет логи без ротации** — `json-file` с пустым конфигом, ни
`max-size`, ни `max-file`. Файл растёт до заполнения диска.

## 1. Контракт уровней (делаем до кода)

Единственное правило, от которого зависит «мусор или польза»:

| Уровень | Когда | Видно в проде |
|---|---|---|
| `fatal` | процесс не может продолжать работу (нет обязательного env, порт занят) | всегда |
| `error` | сломан пользовательский сценарий или упала фоновая задача. **Требует действия** | всегда |
| `warn` | деградация с фолбэком: ретрай выручил, токен протух, платформа ответила 429, кэш пуст | всегда |
| `info` | жизненный цикл и **итоги**: старт/остановка сервиса, результат цикла крона одной строкой, публикация ушла, пользователь вошёл | всегда |
| `debug` | трассировки запросов/ответов, промпты, тела, пошаговый разбор | только при `LOG_LEVEL=debug` |

Три запрета, без которых прод снова зарастёт:

1. **Никаких глушилок по подстроке.** `FILTERED_MESSAGES` и
   `CRITICAL_ERROR_KEYWORDS` удаляются целиком. Уровень определяет автор строки,
   а не поиск по русскому тексту.
2. **Одна строка `info` на итерацию цикла.** Детали внутри итерации — `debug`.
   Ошибки — всегда, независимо от цикла.
3. **Пустой `catch {}` запрещён.** Либо лог с уровнем, либо однострочный
   комментарий, почему тут действительно нечего сказать.

## 2. Этапы

### Этап 1. Один транспорт, работающие уровни

Ставим `pino`. `server/utils/logger.ts` становится тонкой обёрткой:

- вывод — JSON-строка на событие; в development — `pino-pretty`;
- уровень берётся из `LOG_LEVEL`, дефолт `info` в проде, `debug` в dev;
- `redact` на уровне сериализатора: `token`, `access_token`, `refresh_token`,
  `client_secret`, `password`, `apiKey`, `authorization`, `cookie`, `set-cookie`
  — на любой глубине. Ручные `[REDACTED]` по коду постепенно убираем: они
  ненадёжны и уже сейчас закрывают не всё;
- кольцевой буфер `getRecentLogs()` для `/api/debug/logs` сохраняем — он полезен
  и не требует внешнего сборщика;
- **обратная совместимость**: `log`, `log.info/warn/error/debug`, `logMessage`,
  `info`, `warn`, `error`, `debug`, `criticalError`, `systemError` остаются
  экспортами-шимами поверх pino. Ни один из 5800 вызовов не правим.
  `systemError` перестаёт быть dev-only (это была ловушка), `criticalError`
  становится `fatal`.

Приёмка: `LOG_LEVEL=debug` включает трассировки; при дефолтном уровне ни один
`error`/`warn` не теряется; тест на то, что `log(m,s,'error')` и `log.error(m)`
дают одинаковый уровень.

Побочно правим инфраструктуру: в `docker-compose.yml` для `smm` добавляем
`logging.options.max-size=50m`, `max-file=5`.

### Этап 2. Сквозной контекст и честный access-лог

- `AsyncLocalStorage` со `{ reqId, userId, campaignId }`; `reqId` берём из
  заголовка `x-request-id` (Traefik умеет проставлять) либо генерируем;
- middleware пишет **одну** строку на завершение запроса: `method`, шаблон
  роута (`/api/campaigns/:id`, не подставленный id — иначе кардинальность в Loki
  взорвётся), `status`, `durationMs`, `reqId`. Текущий `[HTTP]`-лог на входе
  удаляем;
- `campaignId` кладём в контекст там, где он резолвится (`authorizeCampaignAccess`).

Приёмка: по `reqId` из ответа находится вся цепочка строк этого запроса.

### Этап 3. Границы системы больше не молчат

Единый хелпер `logExternalCall({ system, operation, status, durationMs, reason })`
и его применение в четырёх местах, через которые ходит всё:

- `DirectusCrud.executeRequest` — на любой не-2xx `warn`/`error` с `collection`,
  `status` и `reason` из тела Directus. Заодно: если токен не разрешился,
  запрос уходит анонимно — добавляем явный `allowAnonymous` и громкий `warn` во
  всех остальных случаях (именно это породило половину сегодняшних 403);
- `server/directus.ts` (axios-инстанс) — interceptor на ошибки;
- клиенты соцсетей и скрапера — обёртка вокруг запроса;
- AI-провайдеры — код ошибки и модель, без тела промпта на `info`.

Приёмка: тест, что 403 от Directus порождает ровно одну `error`-строку с
`collection` и `reason`.

### Этап 4. Значимые доменные события

Только там, где событие означает деньги, публикацию или доступ. Стабильные
машинные ключи `event`, по которым потом строятся алерты:

- публикация: `publish.scheduled`, `publish.succeeded`, `publish.failed`
  (`platform`, `contentId`, `campaignId`, `reason`);
- планировщик/кроны: `cron.started`, `cron.finished` (`processed`, `failed`,
  `durationMs`), `cron.failed`;
- автономный режим: `autonomous.cycle_finished`, `autonomous.cycle_failed`;
- авторизация: `auth.login`, `auth.login_failed`, `auth.token_expired`,
  `auth.password_reset_used`;
- тариф/оплата: `plan.changed`, `plan.expired`, `payment.failed`;
- токены платформ: `platform.token_expiring`, `platform.token_expired`.

Приёмка: по каждому пункту есть строка в проде за сутки нормальной работы либо
понятно, почему её нет.

### Этап 5. Вычистить шум

- `analytics trace=` ([analytics-service.ts:41](../server/services/analytics-service.ts:41))
  и `scraper request=` уходят на `debug`; на `info` остаётся один итог на кампанию;
- 56 молчаливых `catch` разбираются: лог или обоснование;
- повторяющиеся `console.log` в горячих путях (`autonomous-ai.ts` — 188 вызовов,
  `storage.ts` — 157, `telegram-bot/index.ts` — 128) переводятся на `debug`
  пофайлово, начиная с самых громких.

Приёмка: за час нормальной работы прод-лог читается глазами целиком.

### Этап 6. Sentry

Ставим только сейчас — на структурированные ошибки с контекстом.

- `@sentry/node`, `tracesSampleRate` низкий, `environment`, `release` = git sha;
- `reqId`/`userId`/`campaignId` из `AsyncLocalStorage` едут как `tags`;
- `beforeSend` прогоняет тот же redact-список;
- в Sentry уезжают `error` и `fatal`; `warn` — нет, иначе шум;
- Express error-handler и `unhandledRejection`/`uncaughtException` подключены.

Приёмка: искусственная ошибка в проде создаёт инцидент с `reqId`, по которому в
логе находится вся цепочка.

### Этап 7. Поиск и алерты по логам

`Grafana Loki + Promtail + Grafana` в том же compose. Promtail забирает
docker json-file, JSON парсится в поля. Алерты в Телеграм:

- `event="publish.failed"` чаще N раз за 15 минут;
- `event="directus.request_failed"` со `status=403` — вообще любой;
- отсутствие `cron.finished` дольше ожидаемого интервала (тихая смерть крона —
  ровно то, что случилось с VK-мониторингом);
- доля 5xx в access-логе.

Sentry отвечает на «что сломалось», Loki — на «что происходило в 17:44» и на
тихие деградации без исключений.
