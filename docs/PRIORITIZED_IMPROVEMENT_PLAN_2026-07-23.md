# Приоритизированный план доработок `smm-video`

Дата: 2026-07-23  
Основание: `docs/zoo-analysis-2026-07-23.md` и повторная точечная проверка упомянутых участков текущего кода.

## Как читать приоритет

Порядок ниже — порядок выполнения по соотношению ценность/цена с поправкой на критичность: устранение активной утечки или возможности межтенантного воздействия идёт раньше обычных улучшений, даже если требует больше работы.

Оценка трудозатрат относительная:

- **low** — локальное изменение, тесты и деплой в пределах примерно одного рабочего дня;
- **medium** — несколько связанных модулей или заметная миграция, примерно 2–5 рабочих дней;
- **high** — архитектурная/операционная миграция, обычно от одной недели.

## Порядок работ

### 1. Удалить публичную выдачу Directus admin token

- **Что делать:** удалить `GET /api/auth/system-token` из `server/api/auth-routes.ts`; заменить возможных внутренних потребителей прямым серверным вызовом; отозвать выданный токен; добавить regression-тест, что анонимный и пользовательский запросы получают `404`.
- **Зачем:** endpoint без аутентификации даёт полномочия сервисного администратора и позволяет полностью обойти прикладную авторизацию.
- **Трудозатраты:** **low**.
- **Почему №1:** максимальный подтверждённый ущерб при минимальной цене исправления.
- **Готово, когда:** route отсутствует в production, старый токен отозван, тест на отсутствие endpoint проходит.

### 2. Закрыть управление глобальным scheduler для обычных пользователей

- **Что делать:** удалить пользовательские `toggle-publishing` и `reset-processed-cache` либо сделать их admin-only; принимать изменение состояния только через `POST`; отделить будущие per-user команды от process-global controls; добавить тесты на `401/403` и запрет GET-мутаций.
- **Зачем:** сейчас любой аутентифицированный пользователь может остановить публикации всех tenants или сбросить общий runtime-state.
- **Трудозатраты:** **low**.
- **Почему №2:** дешёво устраняет межтенантный DoS и опасную GET-мутацию.
- **Готово, когда:** non-admin не может изменить глобальное состояние ни одним HTTP-методом.

### 3. Считать credentials из `.env.example` скомпрометированными и провести ротацию

- **Что делать:** немедленно заменить значения в `.env.example` на явные placeholders; отозвать и перевыпустить Directus, S3, Gemini/Vertex и YooKassa credentials; обновить секреты окружений; проверить audit/access/billing logs; после ротации согласованно очистить Git history и уведомить владельцев clones/forks. До завершения ротации при необходимости ограничить ключи по IP, scope и spend.
- **Зачем:** простое удаление значений из текущего файла не защищает от извлечения ключей из Git history; возможен доступ к данным, хранилищу, AI-бюджету и платежам.
- **Трудозатраты:** **high** из-за координации с провайдерами и окружениями; правка шаблона сама по себе **low**.
- **Почему №3:** ценность критическая, но после быстрых code-hotfixes, поскольку ротация операционно дороже и должна выполняться без потери доступности.
- **Готово, когда:** старые credentials недействительны, production работает на новых, журналы проверены, в шаблоне и актуальной истории нет секретов.

### 4. Ограничить upload endpoint

- **Что делать:** задать небольшой явный лимит Multer; добавить MIME allowlist и проверку magic bytes; генерировать S3 key и расширение на сервере; не возвращать клиенту внутренний `error.message`; для крупных файлов перейти на streaming upload или temp spool; снизить глобальный JSON/urlencoded limit до реально необходимого.
- **Зачем:** текущий `memoryStorage()` без лимитов допускает memory DoS, загрузку произвольного содержимого и неконтролируемые S3 keys.
- **Трудозатраты:** **low** для защитных лимитов и валидации, **medium** для streaming.
- **Почему №4:** базовый защитный слой даёт высокий выигрыш быстро; streaming можно завершить отдельным продолжением.
- **Готово, когда:** oversized и non-image запросы стабильно получают `413/415`, heap не зависит линейно от размера крупных загрузок, внутренние ошибки не раскрываются.

### 5. Временно изолировать WebSocket, затем сделать его user-scoped

- **Что делать:** если realtime не критичен — временно отключить `/ws` в production; затем валидировать Directus session при upgrade, проверять `Origin`, привязывать socket к user/tenant ID и отправлять события только владельцу или разрешённой группе; ввести лимиты размера и частоты сообщений.
- **Зачем:** сейчас неаутентифицированный клиент получает публикационные события всех пользователей.
- **Трудозатраты:** **low** для временного закрытия, **medium** для корректной реализации.
- **Почему №5:** временная мера быстро прекращает утечку, а полная доработка требует изменения модели адресации событий.
- **Готово, когда:** сокет без валидной сессии не подключается, пользователь A не получает события пользователя B.

### 6. Сделать платные и mutating операции fail-closed

- **Что делать:** при недоступности Directus блокировать AI/media/publication mutations; оставить публичные routes и webhooks только в явном allowlist; не пропускать mutating request без identity; при необходимости кэшировать последний подтверждённый entitlement по user ID с коротким TTL.
- **Зачем:** текущий fail-open позволяет использовать платные функции при сбое Directus и делает случайно незащищённый route обходом subscription gate.
- **Трудозатраты:** **medium**.
- **Почему №6:** защищает прямые расходы и публикации; после экстренных утечек и дешёвых периметров.
- **Готово, когда:** тестовый outage Directus закрывает cost-bearing mutations, но документированные публичные callbacks продолжают работать.

### 7. Зафиксировать P0/P1 security regression suite в CI

- **Что делать:** автоматизировать проверки отсутствия `system-token`, admin-only scheduler controls, tenant isolation WebSocket, upload `413/415`, fail-closed subscription; добавить secret scanning для изменений и истории; запускать suite до deploy.
- **Зачем:** исправления затрагивают разрозненные routers/middleware и без тестов легко регрессируют при дальнейшем рефакторинге.
- **Трудозатраты:** **medium**.
- **Почему №7:** после первичных hotfixes тесты превращают их из разовых правок в постоянные гарантии и снижают цену всех следующих этапов.
- **Готово, когда:** каждый перечисленный сценарий падает на старом поведении и блокирует merge/deploy при регрессии.

### 8. Убрать refresh token из `localStorage` и вернуть строгую CSP

- **Что делать:** хранить refresh token в `HttpOnly`, `Secure`, `SameSite` cookie; держать короткоживущий access token в памяти; централизовать клиентский auth adapter вместо прямых чтений `localStorage`; настроить CSRF-защиту; вернуть CSP с точечными `connect-src`/`frame-ancestors` для нужных интеграций.
- **Зачем:** при XSS сейчас похищается долговременная сессия, а отключённая CSP увеличивает вероятность и ущерб атаки.
- **Трудозатраты:** **high**.
- **Почему №8:** высокая security-ценность, но миграция затрагивает сервер, десятки клиентских потребителей и session lifecycle.
- **Готово, когда:** refresh token недоступен JavaScript, logout/rotation/expiry покрыты тестами, приложение работает под включённой CSP.

### 9. Сделать реальный TypeScript check deploy-gate

- **Что делать:** сначала исправить runtime-significant ошибки (`url`, `messageId`, отсутствующие методы, state и modules); разделить frontend/backend tsconfig только для управляемого исправления; довести полный `tsc --noEmit` до нуля; запускать его перед build и в CI, удалить иллюзию проверки семи выбранных файлов.
- **Зачем:** production check сейчас показывает 399 ошибок в 80 файлах, а зелёный esbuild bundle не гарантирует исполнимость кода.
- **Трудозатраты:** **high**; первая runtime-критичная пачка — **medium**.
- **Почему №9:** ценность высокая для надёжности, но объём велик; security-периметр и regression tests должны появиться раньше.
- **Готово, когда:** полный production type-check проходит и является обязательным merge/deploy gate.

### 10. Разделить liveness/readiness и внедрить redacted structured logging

- **Что делать:** оставить `/live` проверкой процесса; в `/ready` с короткими timeout проверять Directus и обязательное хранилище/queue; ввести request ID, уровни и structured logger с redaction; убрать PII, токены, user/admin identifiers и прямые `console.*`; пустые `catch` заменить контролируемыми state transitions и ошибками.
- **Зачем:** текущий `/health` ложно сообщает о готовности, а шумные логи одновременно раскрывают данные и плохо помогают расследовать сбои публикаций.
- **Трудозатраты:** **medium**.
- **Почему №10:** сравнительно недорого повышает наблюдаемость перед сложной миграцией worker/scheduler.
- **Готово, когда:** orchestrator выводит деградировавший instance из rotation, а публикацию можно проследить по content/platform/attempt без чувствительных данных.

### 11. Сделать Docker build воспроизводимым

- **Что делать:** заменить `npm install` на lockfile-driven `npm ci`; исключить повторную установку двух пакетов поверх production tree, корректно классифицировав dependencies; добавить BuildKit cache, dependency audit и SBOM.
- **Зачем:** сейчас один commit может собираться с разными dependency trees, что усложняет откат, аудит и поиск дефектов.
- **Трудозатраты:** **low**.
- **Почему №11:** очень хорошее value/cost, но не перекрывает непосредственные security/runtime риски выше.
- **Готово, когда:** чистые повторные сборки используют lockfile и дают одинаковое дерево зависимостей.

### 12. Перевести публикацию на durable claim и idempotency

- **Что делать:** ввести атомарный DB claim для scheduled content или очередь с lease; хранить job state вне памяти; использовать idempotency key `(content_id, platform, scheduled_version)`; определить retry/backoff/dead-letter и recovery после crash; доказать тестом работу двух workers без дублей.
- **Зачем:** in-memory locks/cache не работают между replicas и исчезают при рестарте, поэтому возможны двойные внешние публикации.
- **Трудозатраты:** **high**.
- **Почему №12:** критично для масштабирования и надёжности, но безопаснее выполнять после тестов, type gate и наблюдаемости.
- **Готово, когда:** два параллельных worker и crash/restart не создают повторной публикации одной версии контента.

### 13. Разделить process roles: web, worker, bot

- **Что делать:** вынести scheduler/AI/media jobs в worker, Telegram bot — в отдельный process role; оставить web-процессу HTTP/SPA/WebSocket; определить отдельные readiness, shutdown, ресурсы и deployment scaling для каждой роли.
- **Зачем:** сейчас CPU/RAM spike или падение одной обязанности ухудшает/останавливает весь продукт.
- **Трудозатраты:** **high**.
- **Почему №13:** большой выигрыш по blast radius, но зависит от durable jobs из пункта 12.
- **Готово, когда:** web можно масштабировать независимо, рестарт bot/worker не прерывает API, shutdown не теряет jobs.

### 14. Унифицировать identity, auth и Directus access

- **Что делать:** свести validation/session/Directus calls к одному проверяемому adapter; брать user/tenant identity только из валидированной сессии; запретить `x-user-id` как источник identity; централизовать role/ownership/entitlement policy.
- **Зачем:** несколько auth-слоёв и разрозненные routers повышают риск пропущенной tenant-проверки и неодинакового поведения.
- **Трудозатраты:** **high**.
- **Почему №14:** системно уменьшает класс auth-дефектов, но миграция широка и должна идти после фиксации поведения тестами.
- **Готово, когда:** routes не доверяют клиентскому user ID, а единый policy layer покрыт unit/integration тестами.

### 15. Декомпозировать крупные модули и уменьшить frontend bundles

- **Что делать:** делить `server/index.ts`, `publish-scheduler.ts`, `autonomous-ai.ts` и social publishing по use case/provider; разбить крупные React pages на feature boundaries; lazy-load тяжёлые routes/editor; устранить mixed static/dynamic imports; поставить bundle budgets.
- **Зачем:** крупные файлы смешивают transport, policy, orchestration и provider logic, повышая цену и риск каждой правки; chunks 762 KB и 675 KB ухудшают загрузку.
- **Трудозатраты:** **high**.
- **Почему №15:** полезно для скорости разработки и UX, но не должно отвлекать от подтверждённых security и correctness рисков.
- **Готово, когда:** границы модулей соответствуют use cases, тяжёлые страницы загружаются лениво, CI блокирует превышение согласованного bundle budget.

## Рекомендуемые волны поставки

1. **Incident/hotfix:** пункты 1–5, включая отзыв system token и начало ротации credentials.
2. **Защитный контур:** пункты 6–8.
3. **Engineering gates и эксплуатация:** пункты 9–11.
4. **Масштабирование и снижение blast radius:** пункты 12–14.
5. **Управляемость кода и performance:** пункт 15.

Каждую волну следует выпускать отдельно с возможностью отката. Очистку Git history выполнять только после ротации credentials и согласования с владельцами remote/forks; она не заменяет отзыв ключей.
