## 1. Что за система

SMM Manager — веб-приложение для ведения соцсетей: кампании, сбор трендов,
генерация и планирование контента, публикация в VK/Telegram/Instagram/Facebook/
Threads/YouTube/TikTok, аналитика.

**Стек:** Node ≥20, Express 4, React 18 + Vite 5, TypeScript. Данные — **Directus
11.2.2** поверх Postgres 16 (приложение почти не ходит в SQL напрямую, а работает
через Directus REST). Тесты — Vitest 4, E2E — Playwright 1.60. Сборка — Docker.

**Ключевая особенность, которую надо понять сразу:** Directus здесь не деталь
хранения, а источник истины и слой прав. Половина инцидентов ниже — это места,
где приложение неверно понимало ответ Directus.

## 3. Деплой — единственный способ

```bash
/root/smm/scripts/deploy-smm.sh              # выкатить текущий origin/main
/root/smm/scripts/deploy-smm.sh --rollback <sha>
```

Скрипт: `flock` (очередь) → `git fetch` → чистый временный worktree ровно на SHA →
сборка → **повторная сверка origin/main** → переключение алиаса `root-smm:deployed`
→ `up -d --no-build` → сверка SHA в трёх местах → ротация старых образов (держим 3).

**Инвариант без исключений:** `origin/main` = `/health.revision` = метка образа =
метка контейнера. Проверка:

```bash
curl -s https://smm.nplanner.ru/health | jq -r .revision
```

Почему так строго:
- `docker compose build smm` **больше не работает и не сообщает об этом** — у
  сервиса нет секции `build:`. Он выходит с кодом 0 и ничего не делает. Старая
  связка `build && up` выглядит успешной и оставляет прежний образ;
- docker берёт контекст из рабочего дерева, а не из HEAD: сборка из `/root/smm`
  утащит в прод чужие незакоммиченные файлы;
- на хосте одновременно работают несколько исполнителей, тег образа общий — кто
  выкатился последним, того версия и осталась.

«Правка не влияет на рантайм» **не** повод пропустить деплой: provenance образа —
это SHA, а не содержимое диффа.

## 4. Как здесь принято работать

1. **Задачу заявить до изменений.** Борд в Slock: `raft task claim`. Прод не
   трогать до claim.
2. **Red-before обязателен.** Тест засчитывается, только если он краснеет при
   снятии фикса. Проверяю снятием, а не «зелено ли». Цифры красных тестов идут в
   передачу.
3. **Четыре проверки перед push:** `npx vitest run`, `npm run check`,
   `npm run check:client`, `npm run build`. Красное не умалчивать.
4. **Один gate и один деплой на инкремент**, а не после каждого коммита.
5. **Jira — выжимка.** Тикет читает заказчик: диапазон коммитов, 1–2 строки сути,
   ссылка. Подробности — файлом в `docs/prompts/`. Командное обсуждение — в Slock,
   не в Jira. Канон: `/root/.config/jira/README.md`.
6. **Jira Server/DC 9.x**: только `Authorization: Bearer $JIRA_TOKEN`, REST **v2**
   (не v3), типы задач по-русски (`Задача`, `Ошибка`), эпик — `customfield_10101`.
   Креды: `/root/.config/jira/env`. Переходы: 11 Сделать, 21 В работе, 31 Готово.
7. **Сообщения в канал дороги:** каждое будит всех агентов. Итог — в канал,
   детали — в репозиторий. Канал полезно держать в mute, задачи приходят через
   @mention и DM.
8. **Коммиты объясняют «почему», а не «что»** — следующий разработчик читает
   `git log`, а не тикет.

## 5. Правила, купленные инцидентами

Это самая полезная часть. Каждое правило стоило поломки на проде.

**Проверять чтением, а не кодом ответа.** `200`/`ok` означает «запрос принят», не
«состояние изменилось». За один день это выстрелило трижды:
- гейт подписки получил от Directus ответ без запрошенных полей и, по строгому
  контракту, закрыл мутации — **все не-админы сутки не могли ничего сохранить**;
- телеграм-бот принял `PATCH 200` за успех и отрапортовал «тариф активирован»,
  хотя в базе ничего не изменилось;
- мой собственный тест проверял объявление константы, а не её применение —
  и молчал, когда значение вернули обратно.

**При изменении гейта сначала проверять разрешающий путь.** Мы тестировали
отсутствие токена, невалидный токен, недоступность Directus — и не проверили
самый обычный случай: обычный пользователь с активной подпиской сохраняет. Fail-
closed ломается молча и целиком, а логов на успешном пути обычно нет.

**Проводку закреплять отдельно от значения.** Модуль может быть правильным и не
подключённым. Пока нет render-тестов, используется source-check: тест читает файл
и проверяет, что нужный вызов там есть (примеры: `background-jobs.test.ts`,
`use-plan-freshness.test.ts`).

**Не создавать данные на проде ради проверки** без явного разрешения владельца.

**Инвариант без исключений лучше удобного исключения.** Один раз согласившись
«тут можно не выкатывать», получаешь спор при каждом следующем деплое.

## 6. Что сломано и как это чинили (чтобы не искать заново)

- **Гейт подписки** (`server/middleware/require-active-subscription.ts`) —
  fail-closed: нет личности → 401, Directus 401/403 → 401, сеть/5xx/непонятный
  ответ → 503 `SUBSCRIPTION_VALIDATION_UNAVAILABLE`. Строго разбирает контракт:
  `expire_date` обязан присутствовать (null или валидная дата), admin-флаги —
  только boolean. **Требует права** `directus_permissions` id 122: роль
  пользователя должна читать свою запись (`id = $CURRENT_USER`) по полям
  `id,expire_date,is_smm_admin,is_smm_super`. Без него прод ложится для не-админов.
- **Одобрение тарифа** (`server/services/apply-subscription.ts`) — пишет и
  **читает обратно**, успех сообщается только при совпадении. Логирует
  `event=subscription.approve`.
- **Глобальные API-ключи** (`server/services/global-api-keys.ts`) — два кеша:
  `keysCache` (список для админки) и `keyCache` (рантайм). При add/update/delete
  рантайм-кеш сбрасывается целиком, иначе смена ключа не применяется до часа.
- **Фоновые задачи** — планировщик публикаций, валидатор статусов, VK-ротация
  токенов, телеграм-бот — стартуют в `server/index.ts` и выключаются флагом
  `DISABLE_BACKGROUND_JOBS`. Второй экземпляр приложения на том же окружении = два
  планировщика и два бота на одной базе.

## 7. E2E-стенд

Отдельный compose-проект `/root/smm-e2e/`: свои Postgres и Directus, слушает
только `127.0.0.1`, traefik-меток нет, внешние токены пустые (соцсети, AI, S3,
платёжка), `DISABLE_BACKGROUND_JOBS=1`. Схема Directus переносится снапшотом,
**боевые данные не копируются**. Тестовый пользователь — обычный, не админ.

```bash
bash /root/smm/e2e/run.sh      # сам ставит нужную сборку браузера
```

Грабли: `docker restart` оставляет старый образ — после выкатки нужен
`docker compose ... up -d --force-recreate smm-e2e`. И `PLAYWRIGHT_BASE_URL`
обязателен: конфиг намеренно падает без него, потому что раньше Playwright
поднимал приложение сам, на боевом окружении.

Последний прогон: **129 исполняемых тестов, 21 красный** (67 пропускаются
условиями внутри спеков). Разбор — AI-60.

## 11. Мелочи, которые экономят часы

- Кириллицу в бандле грепать бесполезно: esbuild экранирует не-ASCII. Ищи
  ASCII-маркеры или, лучше, `/health.revision`.
- `docker logs smm` показывает логи только текущего контейнера.
- В логах приложения нет записей об обычных мутациях — по ним нельзя доказать
  ни успех, ни отказ (это и есть AI-65).
- Бэкапы, оставленные при правках: `/root/.env.bak-*`,
  `/root/directus_permissions.bak-20260801.sql`,
  `/root/docker-compose.yml.bak-ai50-20260731`, образ `root-smm:pre-ai50-*`.
