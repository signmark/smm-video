## Входной ритуал (каждая сессия)

1. `AGENTS.md` → этот файл → `.agents/memory/MEMORY.md`. Для ревью кода обязательна ориентация по `docs/agents/codebase-map.md` (слои роутов, инварианты, метод диагностики).

4. Входящие handoff'ы: свежие `docs/prompts/hermes-*.md` без твоего вердикта = твоя очередь.

## Как ревьюить (обязательный протокол)

Ревью — не чтение диффа, а независимая верификация. По шаблону `templates/review-verdict-template.md`:

1. **Скоуп:** `git show --stat <hash>` каждого коммита — только заявленные файлы? Лишнее = вопрос исполнителю.
2. **Свой прогон, не чужие цифры:** `npx vitest run` + `npx tsc -p tsconfig.critical.json` локально. Числа в вердикт. Расхождение с handoff'ом = блокер.
3. **Инварианты подсистемы:** открыть соответствующий урок в `.agents/memory/` и проверить, что фикс их не нарушает (порядок конвейера, token policy, stock gate и т.д.).
4. **Тест падает без фикса?** Мысленно или реально откати фикс — регрессионный тест обязан покраснеть. Тест, который зелёный всегда, не защищает.
5. **Негативные сценарии:** для security-фиксов — проверить 401/403/404 по всем методам, anonymous + authenticated, GET-мутации.
6. **Вердикт:** блокер (мерж нельзя) / minor (отдельный follow-up) / принято. Каждый блокер — с конкретным файлом/строкой и способом воспроизведения. Не «кажется, тут не так», а «вот вход, вот неверный выход».
7. Файл вердикта: `docs/prompts/mavis-<verdict|review>-<дата>.md`.

**Чего не делать в ревью:** не переписывать код исполнителя самому (single-writer); не пропускать «мелочь, потом поправим» без фиксации follow-up; не подтверждать то, что не проверил лично.
