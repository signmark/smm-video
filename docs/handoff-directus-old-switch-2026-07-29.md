# Переключение на восстановленную БД `directus_old` — 29.07.2026

Фолоуап для следующей сессии.

> **Обновлено 29.07.2026 08:26.** Переключение стало постоянным: базы
> переименованы, боевая `directus` — это теперь данные старого прода, прежний
> форк лежит рядом как `directus_fork_backup`. Откат больше не планируется,
> раздел «Откат» ниже оставлен как история. Актуальное описание — в
> [CLAUDE.md](../CLAUDE.md), раздел «Смена боевой базы 29.07.2026».

## Что сделано

Старый прод `45.130.212.62` (hostname `oladaymbzh`) временно восстановлен и
доступен по ssh с этой машины по ключу. Забраны его дампы за 28 и 29 июля,
md5 сверены с источником.

Дамп `directus_20260729_020001.sql` развёрнут в отдельную БД **`directus_old`**
(2222 МБ, 49 таблиц, восстановился без ошибок). Боевая `directus` не тронута.

Затем по решению владельца **боевой Directus переключён на `directus_old`**:

- `/root/docker-compose.yml` — `DB_DATABASE=${DIRECTUS_DB:-directus}`
- `/root/.env` — добавлена строка `DIRECTUS_DB=directus_old`
- `docker compose up -d directus` (заодно пересоздал контейнер Postgres,
  данные не пострадали — bind-mount `/root/postgres`)

Переключение подтверждено по данным через API: 96 пользователей, 1785 записей
`campaign_content`, 33 589 комментариев — цифры старого прода. При старте
Directus написал `Running migrations... Done` и схему `directus_old` не менял.

## Текущая проблема

Планировщик циклится на 401 (~6 отказов в минуту), публикация не работает.
В UI: шапка показывает «Вход» вместо пользователя, тариф падает в «Базовый».

**Причина — несовпадение служебных кредов между базами, а не код.**

| переменная | боевая `directus` | `directus_old` |
|---|---|---|
| `DIRECTUS_TOKEN` | не найден | не найден |
| `DIRECTUS_STATIC_TOKEN` | валиден | не найден |
| `DIRECTUS_ADMIN_TOKEN` | не найден | валиден |

`resolveServiceToken` в [campaign-access.ts](../server/services/campaign-access.ts)
ходит через `adminTokenManager.getAdminToken()`, который валидирует статический
токен, а при протухании логинится по `DIRECTUS_ADMIN_EMAIL`/`DIRECTUS_ADMIN_PASSWORD`.
В `directus_old` не работает ни одна ветка: токена там нет, а логин отдаёт
`INVALID_CREDENTIALS` — пароль админа в env не совпадает с хешем в этой базе.

Разница в UI между `smm.nplanner.ru` и `smm.omemo.tech` — **не код**. Оба домена
это один контейнер `smm` и один бандл; различается только клиентское состояние
(localStorage + кеш React Query в конкретной вкладке).

### Проверенная ложная версия

Была гипотеза, что последний коммит `38db0416f` не задеплоен: образ собран
28.07 в 19:55:05, коммит датирован 19:58. **Гипотеза неверна.** В работающем
бандле `/app/dist/server/index.js` лежит `async function resolveServiceToken` —
это версия после фикса. Собирали из рабочего дерева, закоммитили тремя минутами
позже. Проверять такое надо по содержимому бандла, а не по датам.

## Откат — не актуально, оставлено как история

Планировался возврат на прежнюю базу через восстановление `.env` из бэкапа
`/root/.env.bak-before-directus_old-20260729-0724`. **Так делать нельзя:** после
снятия того бэкапа вторая сессия правила `.env` — убрала `DIRECTUS_TOKEN` и
`DIRECTUS_ADMIN_TOKEN`, добавила `APP_SIGNING_SECRET`. Восстановление файла
целиком затёрло бы эту работу. Если понадобится менять базу — правится только
значение `DIRECTUS_DB`.

Вместо отката 29.07 в 08:20 сделано переименование: `directus` →
`directus_fork_backup`, `directus_old` → `directus`. Обе базы целы.

## Незакрытый баг, найденный попутно

`profile?.plan || 'basic'` в [use-plan.ts](../client/src/hooks/use-plan.ts) не
различает «пользователь на Базовом» и «запрос профиля не выполнился». Любой сбой
`/api/user/profile` молча роняет платного Pro-пользователя в «Базовый» и
отключает ему блок поддержки. Пользователь видит не ошибку, а правдоподобный
интерфейс более дешёвого тарифа. Нужно различать три состояния: загружено,
грузится, ошибка.
