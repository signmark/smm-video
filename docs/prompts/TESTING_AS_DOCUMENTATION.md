# Тесты как объяснители — конвенция зоопарка

**Статус:** действующая конвенция (Claude, 2026-07-21, по запросу владельца).
**Писатель этого файла:** Claude (правки — через него; чужим — append-комментарии).
**Кому:** всем агентам, пишущим тесты в этом репозитории.

## Зачем

Тест выполняет две работы, а не одну:

1. **Проверяет** код (горит красным при поломке).
2. **Объясняет** код — что за контракт, как модуль вызывать, что сломается,
   если контракт нарушить.

Второе для нашего зоопарка так же важно, как первое. Код фиксит не тот, кто
его писал: любой агент должен уметь взять чужой модуль и починить, не
реконструируя намерение с нуля. **Набор тестов — это исполняемая
спецификация модуля.** Если тест написан как объяснитель, следующий агент
читает тесты и сразу понимает: что модуль обещает, как им пользоваться, где
края. Если тест написан только «на зелёный цвет» — он проверяет, но молчит,
и знание остаётся в голове автора (которого завтра в сессии не будет).

Проблема, которую чиним: агенты пишут тесты в общую кучу, каждый под свою
задачу. Пусть эта куча несёт больше пользы — станет читаемой картой кода.

## Шесть правил

### 1. Имя теста — это контракт, а не механизм

Имя должно читаться как предложение о поведении. Читатель, пробежав список
имён в `describe`, должен понять контракт модуля, не открывая тел тестов.

```
❌ it('test aggregateLatest')
❌ it('works with empty input')
✅ it('дедуп по platform_post_id: при нескольких снапшотах побеждает последний по captured_at')
✅ it('возвращает null, когда все агрегаты скрейпера нулевые — сохранённые метрики не затираются')
```

Хорошие живые примеры в репо: `telegram-html.test.ts`
(«регрессия: экранированный HTML не воскрешает `<p>`»),
`schedule-time.test.ts` («частичная публикация НЕ получает published_at»).

### 2. Регрессионный тест ссылается на инцидент/задачу и на ставку

Когда чинишь баг — тест должен научить следующего агента, *какой инвариант
был нарушен и чем это грозило*. Одна строка комментария или префикс в имени.

```ts
it('Task 8: <pre><code> сохраняет внутренний code тегом, а не литералом', () => {
  // Регрессия: pre-стэш экранировал внутренний <code>, юзер видел литерал.
  expect(toTelegramHtml('<pre><code>x &lt; y</code></pre>'))
    .toBe('<pre><code>x &lt; y</code></pre>');
});
```

Так следующий агент, наткнувшись на этот тест, не «оптимизирует» его обратно
в баг — он видит цену.

### 3. Пример в тесте — это документация вызова

Вход должен быть реалистичным, таким, как модуль вызывают в проде. Читатель
учится использовать модуль по твоему тесту. Даже когда баг в краю — сначала
дай happy-path кейс, показывающий нормальную форму вызова и ответа, потом уже
края. Тест «как правильно» ценнее для будущего владельца кода, чем пять тестов
«как неправильно».

### 4. Комментируй НАМЕРЕНИЕ за неочевидной подготовкой

Особенно моки. Мок без объяснения — загадка: почему он возвращает именно это?
что делает реальный прод-код? Эталон в репо — Task C
(`autonomous-ai-tools.test.ts`): каждый мок снабжён комментарием «прод-код
идёт через createGeminiImageService(), а по неуспехе падает на FAL —
возвращаем success:false, чтобы сработала FAL-ветка». Читатель понимает не
только *что* замокано, но и *почему именно так* и *что происходит в реальности*.

```ts
// Прод-код зовёт aiService.generateContent (не geminiDirect), поэтому
// мокаем именно aiService. Иначе тест уходит в реальный Gemini с таймаутом.
vi.mocked(aiService.generateContent).mockResolvedValueOnce({ ... });
```

### 5. Инвариант контракта — переиспользуемым хелпером, а не копипастой

Если у модуля есть сквозное правило («вывод всегда безопасен для Telegram»),
вынеси его в именованный ассерт и зови из каждого релевантного теста. Правило
формулируется один раз, в одном месте, и служит определением контракта.

Эталон в репо — `expectTelegramSafe(output)` в `telegram-html.test.ts`:
хелпер проверяет, что в выводе нет неподдерживаемых тегов и голых `& < >`.
Любой новый тест зовёт его — и контракт «безопасность для TG» держится
централизованно. Новый агент читает хелпер и сразу знает главный инвариант
модуля.

### 6. Не в общую кучу — рядом с существующим

Перед тем как создать `<модуль>-2.test.ts` или параллельный файл — проверь,
нет ли уже теста на этот модуль, и **расширь его**, а не заводи соседний.
Разрозненные тесты на один модуль в трёх файлах (как было с аналитикой)
— это и есть «куча». Один модуль → один основной тест-файл → `describe`-блоки
по сценариям. `describe` именует юнит и ситуацию, `it` — конкретное поведение.

## Чек-лист перед сдачей тестов

- [ ] По именам `it`/`describe` понятен контракт без чтения тел?
- [ ] Регрессионные тесты ссылаются на задачу/инцидент и ставку?
- [ ] Есть happy-path кейс, документирующий нормальный вызов?
- [ ] Неочевидные моки/подготовка снабжены комментарием «почему так + что в проде»?
- [ ] Сквозные инварианты — переиспользуемым хелпером, не копипастой?
- [ ] Тест лёг рядом с существующими на этот модуль, а не в новый файл?

## Что это НЕ значит (чтобы не переусердствовать)

- Не пиши роман в комментариях к тривиальному тесту (`expect(sum(2,2)).toBe(4)`
  объяснять не надо).
- Не дублируй в комментарии то, что уже ясно из хорошего имени.
- Не превращай тест в туториал по языку/фреймворку — объясняй *этот код*,
  а не «как работает vi.mock».
- Объяснитель — это ясность, не объём. Лишние слова так же вредны в тесте,
  как в коде.
