## Задача

Codex отревьюил 77 коммитов за 27–28 июля и оставил семь actionable-замечаний: два P0 по биллингу
(подделка суммы платежа и повторная активация одного платежа), три P1 (SSRF-обход через
IPv4-mapped IPv6 и отсутствие DNS-валидации; секреты в тексте лога; потеря уведомлений
engagement-watcher при одном канале в двух кампаниях) и два P2 (несуществующие календарные даты
нормализуются в другую дату; `extractPostDate` роняет `/api/campaign-trends` на битом timestamp).

Каждая находка сначала проверена по коду и воспроизведена, затем исправлена с регрессионным
тестом. Источник: ревью Codex, поручение owner'а от 2026-07-28.

## План

Порядок — по приоритету, каждая находка отдельным логическим коммитом.

1. **P0-1 цена.** Вынести валидацию промокода из `routes/promo-codes.ts` в
   `services/promo-validation.ts`. `POST /api/payments/create` перестаёт читать `amount` из body;
   цена = `resolvePlanPrice(planKey)`, скидка = только из промокода, перепроверенного на сервере в
   момент создания платежа. План/сумма/валюта/промокод уезжают в `metadata` платежа.
2. **P0-2 идемпотентность.** Новая Directus-коллекция `payment_activations` с уникальным
   `payment_id` (в текущей схеме её нет — проверено, 48 коллекций, есть только `promo_codes` и
   `promo_code_uses`). Claim-before-activate: вставка записи и есть атомарный захват; конфликт
   уникальности = платёж уже обработан. Один механизм для `/activate` и для webhook; webhook
   берёт метаданные из `verified`, а не из тела.
3. **P1-3 SSRF.** Переписать `ssrf-guard`: полный набор запрещённых диапазонов v4/v6 включая
   `::ffff:`-mapped, DNS-резолв с проверкой всех адресов, pinned `lookup` против rebinding,
   ручная обработка redirect с перепроверкой каждого `Location`. Перевести на него proxy-image,
   video/media proxy и crawler.
4. **P1-4 логи.** Редакция строк (`msg` и строковые значения внутри объектов) по парам
   «имя секрета → значение». Убрать дамп `/me/accounts` в facebook-webhook-direct.
5. **P1-5 watcher.** Ключ состояния = получатель + канал; компьютим события без мутации,
   коммитим состояние только после успешной доставки; сбой одного получателя не трогает других.
6. **P2-6 даты.** Строгая календарная проверка с учётом длины месяца и високосного года.
7. **P2-7 тренды.** Проверять `Number.isFinite(date.getTime())` перед `toISOString()`.

## Риски

- **Создание коллекции в проде.** `payment_activations` создаётся тем же
  `ensureCollectionsExist`-паттерном, что уже работает для `promo_codes`. Операция аддитивная,
  существующие данные не трогает. Если создание не удалось — активация должна **падать**, а не
  молча пропускать защиту (fail-closed).
- **SSRF-фикс может сломать легитимные URL.** Основной риск — CDN соцсетей за CNAME и IPv6.
  Митигация: блокируем по фактическим адресам, а не по имени; тест на public → public redirect.
- **Редакция логов может съесть полезное.** Режем только значение после известного имени поля,
  само имя и остальной текст сохраняем.
- **Смена сигнатуры `diffAndUpdateState`** ломает существующий `engagement-watcher.test.ts` —
  тесты обновляются в том же коммите.
