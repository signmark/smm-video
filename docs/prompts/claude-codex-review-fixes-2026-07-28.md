## План

Порядок — по приоритету, каждая находка отдельным логическим коммитом.

1. **P0-1 цена.** Вынести валидацию промокода из `routes/promo-codes.ts` в
   `services/promo-validation.ts`. `POST /api/payments/create` перестаёт читать `amount` из body;
   цена = `resolvePlanPrice(planKey)`, скидка = только из промокода, перепроверенного на сервере в
   момент создания платежа. План/сумма/валюта/промокод уезжают в `metadata` платежа.
2. **P0-2 идемпотентность.** Новая Directus-коллекция `payment_activations` с уникальным
   `payment_id` (в текущей схеме её нет — проверено, 48 коллекций, есть только `promo_codes` и
   `promo_code_uses`). Claim-before-activate: вставка записи и есть атомарный захват; конфликт
   уникальности = платёж уже обработан. Один механизм для `/activate` и для webhook; webhook
   берёт метаданные из `verified`, а не из тела.
3. **P1-3 SSRF.** Переписать `ssrf-guard`: полный набор запрещённых диапазонов v4/v6 включая
   `::ffff:`-mapped, DNS-резолв с проверкой всех адресов, pinned `lookup` против rebinding,
   ручная обработка redirect с перепроверкой каждого `Location`. Перевести на него proxy-image,
   video/media proxy и crawler.
4. **P1-4 логи.** Редакция строк (`msg` и строковые значения внутри объектов) по парам
   «имя секрета → значение». Убрать дамп `/me/accounts` в facebook-webhook-direct.
5. **P1-5 watcher.** Ключ состояния = получатель + канал; компьютим события без мутации,
   коммитим состояние только после успешной доставки; сбой одного получателя не трогает других.
6. **P2-6 даты.** Строгая календарная проверка с учётом длины месяца и високосного года.
7. **P2-7 тренды.** Проверять `Number.isFinite(date.getTime())` перед `toISOString()`.

## Риски

- **Создание коллекции в проде.** `payment_activations` создаётся тем же
  `ensureCollectionsExist`-паттерном, что уже работает для `promo_codes`. Операция аддитивная,
  существующие данные не трогает. Если создание не удалось — активация должна **падать**, а не
  молча пропускать защиту (fail-closed).
- **SSRF-фикс может сломать легитимные URL.** Основной риск — CDN соцсетей за CNAME и IPv6.
  Митигация: блокируем по фактическим адресам, а не по имени; тест на public → public redirect.
- **Редакция логов может съесть полезное.** Режем только значение после известного имени поля,
  само имя и остальной текст сохраняем.
- **Смена сигнатуры `diffAndUpdateState`** ломает существующий `engagement-watcher.test.ts` —
  тесты обновляются в том же коммите.

## Что сделано

Все семь находок закрыты кодом и регрессионными тестами. Ложных среди них не было.

1. **Цена платежа.** `amount` из тела запроса больше не читается. Базовая цена — из
   `resolvePlanPrice`, скидка — только из промокода, перепроверенного на сервере в момент
   создания платежа. Невалидный или просроченный код скидки не даёт: платёж не создаётся,
   возвращается 400 с причиной. План, сумма, валюта и промокод фиксируются в `metadata`.
   Правила промокода вынесены в `services/promo-validation.ts` и переиспользуются
   `/api/promo/validate`, чтобы витрина и платёж не разошлись.
2. **Идемпотентность активации.** Захват платежа в журнале идёт до активации; захватом
   служит сама вставка строки с уникальным `payment_id`, поэтому он атомарен между
   инстансами. Повторный запрос не двигает `expire_date`, не шлёт уведомление и не
   дублирует postback. Один механизм на `/activate` и webhook. Активация смотрит только на
   объект, повторно полученный из ЮКассы, и проверяет `status`, `paid`, `currency`,
   `amount` (сверяется с записанной при создании) и `metadata`. Webhook берёт из тела
   только id платежа.
3. **SSRF.** Адрес разбирается в байты, mapped/compatible/NAT64/6to4 разворачиваются во
   вложенный IPv4. Полный набор запрещённых диапазонов v4/v6. `resolveSafeUrl` резолвит имя
   и отклоняет URL, если запрещён любой адрес. `utils/safe-http.ts` пиннит соединение на
   проверенный адрес и валидирует каждый `Location` вручную.
4. **Секреты в логах.** `redactText` режет значение по имени поля и по схеме Bearer/Basic,
   работает и для `key=value`, и для JSON-строк. Применяется до сборки строки, поэтому
   покрывает stdout, `recentLogs` и dev-вывод. `facebook-webhook-direct` больше не пишет
   ответ `/me/accounts` целиком.
5. **Engagement watcher.** Ключ состояния — «получатель::канал»; опрос канала остаётся один
   на цикл. Состояние подтверждается только после успешной доставки; сбой одного получателя
   не трогает остальных.
6. **Даты.** Календарная проверка с длиной месяца и високосным годом (включая правило
   столетий). Несуществующая дата проваливает разбор целиком, а не теряется.
7. **Тренды.** `msToIso` проверяет `Date#getTime()` перед `toISOString()`; битая запись даёт
   `null` вместо 500 на всю выдачу.

## Компромиссы и отклонения

- **Журнал платежей деградирует в память, если Directus-журнала нет.** Обнаружено уже
  после первой выкатки: у сервисного токена нет прав на создание коллекций (403 и на
  `GET /collections/payment_activations`, и на `POST /collections`). Изначальный
  fail-closed в этом состоянии давал 500 на каждый оплаченный платёж — человек заплатил и
  не получил подписку, что хуже исходной дыры. Запасной путь в памяти процесса слабее
  (не переживает рестарт, не виден второму инстансу), но гасит массовый случай: обновление
  страницы успеха, гонку webhook'а с ручной активацией, ретрай ЮКассы. Каждая деградация
  логируется уровнем error. Как только коллекция и права появятся, код сам вернётся на
  durable-путь.
- **Пиннинг адреса есть не везде.** `safeGet` (axios) пиннит соединение на проверенный
  адрес через `lookup` у `http.request`. Node'овский `fetch` такого параметра не принимает,
  а undici-dispatcher потребовал бы объявить `undici` в зависимостях — попытка сделать это
  подтянула в lock-файл лишние изменения (заодно переписала диапазон typescript), и я
  откатил. Поэтому `safeFetch` даёт DNS-валидацию и ручную проверку redirect'ов, но не
  пиннинг: остаётся узкое окно rebinding для video/media proxy и crawler — они за
  `authenticateUser`. Публичный `/api/proxy-image`, ради которого находка и заведена,
  защищён полностью.
- **Невалидный промокод отклоняет платёж (400), а не молча считает полную цену.**
  Пользователь рассчитывал на другую сумму; тихо списать больше — хуже, чем отказать.
- **`/api/promo/validate` переведён на общий валидатор.** Формально это соседний роут, но
  дублирование тех же правил — прямая причина расхождения витрины и платежа.

## Что было не так и что сделано

### P0-1. Журнал платежей оставался process-local

Первая волна ввела запасной журнал в памяти при недоступности Directus. Коллекции
`payment_activations` в проде не было — значит журнал был в памяти **всегда**, и после
каждого рестарта контейнера старый успешный `paymentId` активировался заново. Мой
прежний размен «лучше память, чем 503 оплатившему» был неверен: он сохранял
небезопасное поведение ради доступности.

- Запасной путь удалён целиком (`memoryLedger` в прод-бандле — 0 вхождений).
- `isLedgerReady()` — проверка готовности; `/api/payments/available` отдаёт
  `available:false`, `/create` возвращает 503 **до** обращения к ЮКассе.
- Уже оплаченный платёж при недоступном журнале получает повторяемую 503; webhook
  отвечает 503 и получает повтор уведомления, а не ложный успех.
- Неатомарный перехват stale-захвата убран: два процесса могли прочитать одну
  запись, оба сделать PATCH и оба выдать подписку. Протухшая заявка помечается
  `needs_reconciliation` и отдаёт 409 — разбор вручную, без CAS не перехватываем.

### P0-2. Скидочные промокоды не расходовались

Промокод только проверялся и уезжал в metadata; ни `promo_code_uses`, ни `used_count`
в платёжном потоке не создавались.

Введена коллекция `promo_reservations` с тремя уникальными индексами одной строки:
`payment_id` (одна бронь на заказ), `user_lock` = `<promo>:<user>` (один код одному
пользователю), `slot_lock` = `<promo>:#<n>` (n-е использование). Вставка либо проходит
целиком, либо отвергается по первому занятому ключу — проверка и захват неразделимы.
`max_uses` соблюдается через слоты, без read-then-increment: проигравший гонку берёт
следующий номер.

Якорь брони — собственный `order_id`: бронь берётся до создания платежа, когда id
ЮКассы ещё не существует. Отменённый платёж код не сжигает — бронь освобождается по
подтверждённому статусу от ЮКассы, а не по таймауту.

**Дефект, найденный при разработке:** отказ «исчерпан» срабатывал по счётчику раньше,
чем проверка «держатель слота мёртв», поэтому брошенная оплата блокировала код
навсегда. Освобождение вынесено перед отказом (`reclaimDeadReservations`).

### P1-3. Старые платежи обходили проверку суммы

Отсутствие `metadata.amount` считалось legacy-случаем с пропуском сверки — это
оставляло рабочими дешёвые платежи, созданные до фикса подделки `amount`. Теперь fail
closed: платёж без `metadata.amount`/`currency` автоматически не активируется,
только ручная сверка.

### P1-4. SSRF был закрыт только предварительной проверкой

- `safeFetch` резолвил имя, а затем глобальный `fetch` резолвил его **заново** — окно
  DNS rebinding оставалось. Соединение переведено на `node:http`/`https` с `lookup`:
  в него отдаётся ровно проверенный адрес. Новых зависимостей не потребовалось.
- Найден дефект: `body` строился жадно через `Readable.toWeb`, что переводит поток в
  web-режим и ломает последующий `arrayBuffer()`. Сделан ленивым.
- Краулер: проверка стояла в роуте, а `page.goto`/`axios.get` резолвили заново;
  `credentials.loginUrl` не проверялся вовсе; прямые вызовы `webCrawlerAgent` из
  `ai-service`, `autonomous-ai` и `campaigns` защиты не получали. Проверка основного
  URL и `loginUrl` перенесена **внутрь агента** — её получают все вызывающие.
- **Браузерный обход выключен** (`WEB_CRAWLER_BROWSER_ENABLED`, по умолчанию false).
  Chromium резолвит имена сам, поэтому наша проверка не распространяется ни на
  навигацию, ни на подресурсы, ни на редиректы; перехват запросов отдаёт URL, но не
  адрес, в который тот развернётся. Надёжной изоляции без пиннинга резолвера всего
  браузера нет. Функция краулера сохранена — обход идёт безопасным HTTP-клиентом,
  ценой неисполнения JS на странице.

## Грабли Directus (для следующего раза)

1. `POST /collections` **без `schema: {}`** создаёт «папку» — запись в
   `directus_collections` без таблицы. Любой `/items/<коллекция>` после этого отвечает
   403 даже админу. Я на это наступил и потратил на диагностику лишний круг.
2. Нужен явный PK-field, иначе коллекция с `fields` не создаётся.
3. `GET /fields/<collection>` отвечает 403 даже под ролью с `admin_access: true`,
   хотя `POST /collections` разрешён. Проверять схему приходится функционально.
4. Существующая коллекция не обновляется автоматически — новые поля надо досоздавать
   отдельно (`ensureFields`).
