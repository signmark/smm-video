### 1. Закрыть cross-tenant storage fallback

Обязательные инварианты:

- пользовательский handler никогда не продолжает чтение чужими/служебными
  токенами после 403/404 пользовательского токена;
- служебное чтение существует только как отдельный явно привилегированный API
  и вызывается после подтверждённого ownership;
- `status`, `cancel`, `mark-as-published`, `update-content`, `direct-schedule` и
  остальные handlers в `publishing-routes.ts` заново проинвентаризированы;
- `cancel` перед любым privileged access вызывает
  `assertContentBelongsToRequester` и не вызывает
  `updateCampaignContent` без корректного токена;
- нельзя кешировать токен запросившего пользователя под `userId`, взятым из
  непроверенного/чужого content;
- Directus 403/404 наружу не превращается в 500 и не раскрывает существование
  чужой записи.

Не делай косметическую заплатку только в одном handler: убери саму возможность
cross-user fallback в пользовательском пути storage. Если фоновые задачи
действительно нуждаются в служебном доступе, раздели методы именами и типами,
чтобы привилегированный вызов был виден в коде.

Регрессионные тесты:

- атакующий с валидной сессией и UUID чужого content получает 404;
- storage/directus privileged GET и PATCH после отказа ownership не вызваны;
- `/api/publish/cancel/:id` не меняет чужую запись даже при прогретом token
  cache и настроенном service token;
- `/api/publish/status/:id` не возвращает чужой статус;
- свой content продолжает отменяться и читаться.

### 2. Связать trend/source с фактической кампанией

Исправь:

- `/api/trends/collect-comments`;
- `/api/trends/collect-comments-single`;
- `/api/analyze-comments`, включая `level=source`.

Не доверяй паре `campaignId + trendId` из тела. Загрузи тренд сервером,
нормализуй relation `campaign_id` как scalar/object и авторизуй фактическую
кампанию объекта. Для списка каждый trend должен принадлежать разрешённой
кампании; смешанный список own+foreign должен завершаться fail-closed до
отправки задания scraper. Для source-level проверь принадлежность фактического
source до admin-записи.

Регрессионные тесты:

- своя кампания + чужой trendId → 404, без scraper/admin write;
- смешанный список own+foreign → полный отказ, без частичного запуска;
- чужой source через `level=source` → 404, без update;
- ошибка Directus при проверке → 503, не «разрешить»;
- собственные trend/source работают.

### 3. Сделать reconciliation-брони действительно fail-closed

Обязательные инварианты:

- запись с `needs_reconciliation=true` не освобождается age-based reclaimer;
- после создания внешнего платежа его YooKassa ID сохраняется вместе с
  reconciliation state, даже если обычный attach-path упал;
- PATCH reconciliation-маркера проверяет `res.ok`; ошибка видима вызывающему
  или гарантированно попадает в отдельный durable retry/outbox;
- ответ cancel `200` со статусом не `canceled`, статус `succeeded` и сетевой
  сбой считаются неоднозначными и не освобождают слот;
- поздний webhook успешного платежа не встречает автоматически освобождённую
  бронь;
- CAS `reserved → completed/released` остаётся единственным переходом состояния.

Не полагайся только на boolean-маркер, запись которого может упасть тем же
Directus-сбоем, что сломал attach. Используй известный `paymentId` при
reconciliation и спроектируй консервативный путь: лучше временно удержать слот,
чем переиспользовать скидку живого платежа.

Регрессионные тесты:

- attach падает, cancel не подтверждён, проходит >30 минут, новый reserve не
  освобождает слот;
- cancel возвращает `succeeded` — тот же результат;
- поздний webhook завершает исходную бронь и подписку;
- PATCH reconciliation 500 не логируется как успех;
- подтверждённый `canceled` по-прежнему освобождает слот;
- конкурентные complete/release сохраняют ровно одного победителя.

### 4. Исправить TOCTOU и бюджет слотов

- После свежего `occupiedSlots()` не добавляй проигранный ранее слот, если его
  уже нет в фактическом состоянии.
- Добавь тест: unique conflict, победитель освобождает слот до перечитывания,
  проигравший успешно занимает освободившийся слот.
- Убери ложный отказ для 201+ синхронных покупателей безлимитного промокода.
  Бюджет должен зависеть от наблюдаемого прогресса/конкуренции, а не содержать
  скрытую бизнес-ёмкость 200.
- Сохрани ограничение `max_uses` и уникальность слотов под конкурентной
  нагрузкой.

### 5. Довести SM-9

Используй единые helpers из `client/src/lib/date-utils.ts`:

- `PublicationCalendar` должен сравнивать календарные ключи по Москве, а не
  локальные `startOfDay/isSameDay`;
- dashboard «сегодня» и «эта неделя» должны считаться по московским границам;
- `posts/index.tsx` не должен обходить нормализацию timestamp без timezone.

Не вводи timezone кампании в этой задаче: текущий контракт сервера — московский
ввод и московское отображение.

Тесты выполняй при `TZ=UTC` и включи граничный пример
`2026-07-28T22:00:00Z == 2026-07-29 01:00 Europe/Moscow`.

### 6. Перепроверить video-temp без расширения публичной поверхности

Код менять только если тесты покажут обход. Добавь table-driven проверки:

- `%2e%2e`, `%2f`, двойной слэш, trailing slash, UUID с хвостом;
- смешанный регистр;
- `POST`, `PUT`, `PATCH`, `DELETE`;
- `X-HTTP-Method-Override: GET` на POST.

Публичными должны остаться только точный UUID и `GET/HEAD`.

## Компромиссы и отклонения

Нет разрешения ослаблять tenant boundary ради обратной совместимости. Для
фоновых задач допустим отдельный privileged API, но не неявный fallback из
пользовательского метода.

CI/CD не входит в этот фикс. После release blockers остаётся согласованный план:
17 client type errors → CI без CD → postdeploy smoke → Playwright.
