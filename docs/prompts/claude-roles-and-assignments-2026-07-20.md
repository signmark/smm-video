## Модель ролей: роли кочуют, счёт остаётся

Роли — ПМ/оркестратор (пишет ТЗ, сверяет исполнение, коммитит),
разработчик, ревьюер, аналитик — это **шляпы на задачу, а не должности**.
Любой агент может взять посильную задачу в любой роли.

Исключение, закреплённое владельцем: **Claude — бессменный
архитектор-ревьюер** (старший в подчинении владельца). Его лимит —
дефицитный ресурс, расходуется по приоритету:

1. Ревью фичевых диффов **до пуша** и приёмка калибровочных сдач.
2. Арбитраж: спорные архитектурные решения, конфликты вокруг `DO NOT FIX`,
   разногласия исполнитель↔верификатор.
3. Ревью коммитов → датированные follow-ups с приёмкой.
4. Кросс-модельная вычитка чужих ТЗ.

На Claude **не** тратить: bulk-исполнение, механику коммитов, рутинные
прогоны тестов — это работа быстрого контура и Mavis. Старшинство не
отменяет правил: вычитка работ Claude другой моделью обязательна, как
и для всех (Codex уже ловил его ошибки — система работает).

Что не кочует:

1. **Леджер доверия** (таблица ниже): «посильность» определяется не
   самооценкой, а показанным счётом в этой роли. Первая задача в новой
   для агента роли — всегда калибровочного размера (ограниченный радиус,
   машинно-проверяемая приёмка).
2. **Протокол взятия задачи:** прежде чем начать, агент (а) вписывает
   себя в таблицу раздачи — это защита от двух исполнителей на одной
   задаче; (б) назначает себе вторую пару глаз — агента на **другой
   модели** — и вписывает её туда же. Задача без назначенного
   верификатора считается не взятой. Владелец может переназначить всё.
3. **Инварианты процесса** (не зависят от того, кто в какой шляпе):
   исполнитель ≠ верификатор; «закрыто = закоммичено»; коммит явным
   списком файлов; один агент — одна задача; `DO NOT FIX` неприкосновенен;
   финальное слово — у владельца.

Основание: наблюдаемые результаты в этом репо (коммиты `299becb`,
`6ec4ad4`, `deddb75`, `0d117a5`, `d680977`, `97947ae`; вычитка промптов

## Совместное редактирование доков: один файл — один писатель

Урок 2026-07-20: Claude и Mavis (оба — медленные длинные сессии) правили
одни и те же доки вперемешку; итог — упавшие правки по устаревшему
состоянию и артефакт слияния в этом самом файле (осколок старого абзаца
провисел в п. 3 «Что не кочует» три ревизии).

1. **У каждого общего файла — единственный писатель.** Реестр:
   - `claude-roles-and-assignments-*.md`, `review-follow-ups-*` за
     авторством Claude — пишет **только Claude**;
   - `README.md`, `baseline-vitest-*.txt` — пишет **только Mavis**;
   - `<автор>-*.md` (ревью, срезы, отчёты, инструкции) — пишет только
     автор из имени файла;
   - промпты `codex-*.md` и аналогичные ТЗ — писатель тот, кто их
     составил; после раздачи файл заморожен (исполнитель не правит ТЗ).
2. **В чужой файл — только append-комментарии.** Если нужно оставить
   статус/замечание в чужом доке — дописать в конец соответствующей
   секции строку вида `> [Имя, дата]: текст`, никогда не менять и не
   удалять существующие строки. Крупные вещи — отдельным своим файлом
   со ссылкой (образец: `codex-task6-review-2026-07-20.md`).
3. **Перечитать перед правкой.** Перед редактированием общего файла —
   свежее чтение с диска, а не правка по памяти из своего контекста:
   файл мог измениться с прошлого взгляда. Упавшая правка (несовпадение
   текста) — это сигнал перечитать, а не продавить.
4. **Правки доков коммитятся сразу**, не копятся в дереве: закоммиченный
   файл — единственная точка синхронизации между сессиями. Именно
   незакоммиченные пачки правок двух авторов и дают коллизии.

## Диспетчеризация и застревания

Урок 2026-07-20: после сдачи Task D и подтверждения прод-бага (Task 9)
конвейер простоял ~2 часа — все ждали, что «кто-нибудь подхватит».

1. **Папка `docs/prompts` — почтовые ящики, а не диспетчер.** Ни один
   агент не опрашивает её в фоне (кроме мониторинга Claude, который
   только читает и пишет ревью). Агент начинает работу тогда, когда
   владелец открыл ему сессию и вручил промпт. Написанная задача ≠
   розданная задача.
2. **Каждая новая задача получает явного адресата в момент записи.**
   Формулировка «быстрый контур» или «любой свободный» допустима только
   в очереди; при переводе в работу владелец называет конкретное имя.
   Claude в follow-ups помечает нерозданное как «ждёт раздачи».
3. **Эскалация застреваний.** На проходе мониторинга Claude явно
   перечисляет владельцу всё, что застряло: принятая сдача не
   закоммичена; hotfix без исполнителя; push давно не делался.
   Застрявший hotfix прод-бага — всегда первая строка эскалации.
4. **Fallback при простое диспетчера** (владелец недоступен, работа
   стоит): Claude имеет право закоммитить принятую им сдачу явным
   списком файлов и выполнить микро-фикс (≤ ~5 строк) с обязательной
   последующей верификацией другой моделью. Право на fallback — только
   когда обычный путь очевидно стоит, и каждое применение фиксируется
   в follow-ups отдельной пометкой.
5. **Адресация: всегда имя + роль.** Прецедент: Mimo/Mavis перепутаны
   при раздаче коммит-задачи. В инструкциях, раздачах и отчётах писать
   «Mavis (оркестратор)», «Mimo (деплой)» — имена похожи, роли разные.
   Файлы инструкций именуются `<адресат>-<суть>-<дата>.md`; исполнитель,
   получивший файл с чужим именем в заголовке, останавливается и
   переспрашивает, а не выполняет.

## Два контура мощности

У зоопарка два типа исполнителей, и это ресурс, а не проблема:

- **Быстрый контур** — Codex, MiniMax (после калибровки): bounded-задачи
  по готовым ТЗ, последовательные цепочки (C→D), всё, чего кто-то ждёт.
- **Фоновый контур** — Kimi: задачи, где сутки задержки ничего не стоят,
  а тщательность решает — системный анализ, тонкая конкурентность,
  ревью фичевых диффов до пуша (при цикле «пуш сегодня, деплой завтра»
  латентность укладывается).

Правило распределения: **медленной мощности не давать срочную работу,
быстрой — тонкую**. Скорость исполнителя — не показатель доверия;
показатель доверия — счёт принятых коммитов.

## Правило двух пар глаз

Вторая пара глаз назначается при взятии задачи (см. протокол выше),
кем бы ни был исполнитель:

- **ТЗ и доки**: кто бы ни писал — **обязательная вычитка агентом на
  другой модели** до раздачи. Вычитка ловит фактические ошибки дёшево —
  проверено трижды (Codex ловил ошибки и у Claude, и в общих промптах).
- **Код уровня фичи** (несколько файлов, прод-поведение): ревью второй
  моделью **до пуша**, а не после. Обе находки по `97947ae` (Task 6, 7)
  были сделаны по уже закоммиченному коду — так больше не делаем.
- **Мелкие bounded-задачи** по готовому промпту: достаточно верификации
  Mavis (дифф + тесты + скоуп).
- **Кросс-модельная верификация.** Mavis и исполнитель MiniMax — одна
  модель, а слепые зоны модели коррелируют: она не увидит в чужой работе
  тот класс ошибок, который делает сама. Поэтому задачи, исполненные
  MiniMax, перед коммитом проходят содержательную проверку агентом на
  другой модели (Codex или Claude); Mavis выполняет механическую часть
  (скоуп, тесты, коммит явным списком). Для Task C (калибровка) это
  обязательно. Общий принцип: исполнитель и содержательный верификатор —
  разные модели, где это осуществимо.

## Калибровка (первая задача агента в новой для него роли)

Относится и к новым участникам, и к смене шляпы опытным (разраб впервые
берёт роль ПМ — это тоже калибровка). Первая задача — с ограниченным
радиусом поражения (текущий пример — MiniMax на Task C: только
тест-файлы, прод не затрагивается, приёмка машинно-проверяема).
Оценка сдачи по чек-листу:

1. **Полнота** — все пункты ТЗ закрыты, `git grep` по критериям приёмки чист.
2. **Дисциплина скоупа** — не полез «улучшать» соседнее; out-of-scope
   находки — отдельным сообщением, не правкой.
3. **Качество по сути, не по форме** — для C особо: моки не подогнаны под
   зелёный цвет ценой смысла теста; ковровый `it.skip` запрещён промптом.
4. **Честность отчёта** — полный `npx vitest run` до/после, преждесуществующие
   падения отмечены явно, дельта против `baseline-vitest-2026-07-19.txt`.

Чистая сдача → перевод в основной ростер, вторая задача уровнем выше
(Task 8 — один файл прод-кода с сильным тестовым покрытием).
Грязная сдача → разбор, вторая калибровочная попытка на задаче того же
класса. Два провала подряд — вопрос к владельцу о составе.

Чего MiniMax не давать до перевода в основной ростер: Task 6 (тонкая
конкурентность), прод-поведение публикаций, что-либо из конвергенции
иерархий.

## Правила (напоминание, полный текст в README)

- Один исполнитель — один файл-промпт, `Out of scope` жёсткая.
- Коммитим только свои файлы явным списком; `git add -A` запрещён;
  чужой WIP не трогать.
- «Подтверждено репродукцией» перепроверять пробой.
- `DO NOT FIX`-секции не пересматривать без явного запроса владельца.
- Закрыл задачу из follow-ups — отметь в том же follow-ups-файле.
- **Новое: «закрыто» = «закоммичено».** Задачу нельзя помечать закрытой
  в follow-ups, пока её код лежит незакоммиченным WIP в дереве: один
  сброс дерева — и «закрытая» задача испаряется, один чужой широкий
  коммит — и она уезжает вперемешку с чужой работой. Порядок: сдал →
  ревью → Mavis закоммитил явным списком файлов → пометка «закрыто»
  с хешем коммита. (Прецедент: Task 2 был помечен закрытым при
  незакоммиченном коде, параллельно с чужим WIP в том же дереве.)
- Номера строк в промптах — на момент написания; при дрейфе искать grep'ом.
