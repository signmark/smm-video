## 1. Диапазон коммитов

`db32cbe8e..<tip ветки fix/ai-37-gitleaks-history>`

Фактический конечный SHA указывается в комментарии тикета при передаче и при
закрытии: док пишется до коммита, который его же и добавляет, поэтому
зашитый сюда хеш всегда отстаёт на один коммит.

## 2. Что было и что стало

§7 закрыт коммитом `7c9c311b0` (пять шагов качества в CI). Скан секретов
добавлен позже, `a80bcc30c`, но только по рабочему дереву:
`gitleaks detect --no-git --source /repo`. То есть ловится секрет, который
добавляют **сейчас**; то, что уже лежит в старых коммитах, не проверялось
ничем — при том, что из GitHub оно выгружается даже после удаления файла.

Добавлен отдельный джоб `secrets-history`: `gitleaks detect` без `--no-git`,
с `fetch-depth: 0`, по расписанию (еженедельно, пн 03:00 UTC) и по кнопке
`workflow_dispatch`. Отчёт JSON выгружается артефактом `gitleaks-history-report`,
в лог печатается сводка по правилам.

## 3. Две ловушки, ради которых это сделано именно так

**Ловушка 1 — `fetch-depth`.** `actions/checkout@v4` по умолчанию берёт **один
коммит**. Если просто снять `--no-git` с существующего шага, gitleaks
просканирует один коммит и честно отчитается `no leaks found`. Гейт будет
выглядеть рабочим и не проверять ничего. Это худший исход из возможных, хуже
отсутствия гейта. Поэтому у нового джоба `fetch-depth: 0`.

Я наступил на ровно эту ловушку при первом прогоне: запустил скан на git-worktree,
где `.git` — файл-указатель, а не каталог. Контейнер его не увидел, gitleaks
отчитался `0 commits scanned` и `no leaks found`. Если бы я не посмотрел на число
коммитов, а поверил слову «no leaks», я бы закрыл задачу зелёным нулём.

**Ловушка 2 — цена.** Полный клон это 9576 коммитов и ~127 МБ. Вешать
`fetch-depth: 0` на каждый push значит замедлить весь CI ради данных, которые
между коммитами не меняются. История проверяется по расписанию отдельным джобом;
`checks` и `secrets` помечены `if: github.event_name != 'schedule'`, чтобы ночью
не гонять тесты вхолостую.

коммитах. Распределение по правилам:

| 117 | jwt |
| 92 | gcp-api-key |
| 48 | private-key |

Файлы-лидеры: `.env.prod` (57), `data/autonomous-states.json` (51),
`SECRETS_FOR_NEW_AGENT.md` (34), `.env` (33), `ALL_SECRETS_FOR_NEW_AGENT.txt` (28),
`playwright/.auth/user.json` (16).

Блокирующий гейт на этом остановил бы работу всей команде и ничего бы не починил:
из истории находки убираются только переписыванием истории, а то, что реально
утекло, чинится **ротацией** — это `AI-46` (`blocked`, `prod-risk`), не эта задача.
Поэтому шаг `continue-on-error` с артефактом, а снятие `continue-on-error` —
после разбора, отдельной задачей.

Значения секретов нигде не печатаются: везде `--redact`, в отчёте пути и правила.
В бакет Beget (второй пункт описания AI-37) я не лез — это AI-46.

## 5. Чем доказано

- **Команда джоба прогнана на проде как есть**, включая нетривиальный случай:
  каталог отчёта `gitleaks-out` лежит ВНУТРИ `:ro`-монтирования `/repo`, а пишется
  через отдельный rw-mount `/out`. Работает: 9576 коммитов просканировано, отчёт
  1198168 байт на месте.
- **Число коммитов проверено явно** (`9576 commits scanned`), а не по фразе
  «no leaks found» — см. ловушку 1.
- **YAML провалидирован** (`yaml.safe_load`): джобы `checks`, `secrets`,
  `secrets-history`; триггеры `push`, `pull_request`, `schedule`, `workflow_dispatch`.
- **Выражение сводки jq прогнано** на реальном отчёте — даёт таблицу выше.
- **Блокирующий джоб `secrets` остался зелёным**: `--no-git` скан рабочего дерева
  на ветке — `no leaks found`, exit 0.

## 6. Что НЕ сделано и почему

**1. Реальный прогон джоба в GitHub Actions НЕ проверен.** Это главный пробел,
и он именно того сорта, против которого написан весь этот джоб. С прода нет
доступа к GitHub API (репозиторий приватный, `gh` не установлен, API отдаёт 404),
поэтому увидеть результат прогона я не могу. Проверено всё, что можно проверить
локально: сами команды, YAML, mount, jq. Не проверено: как GitHub исполнит
`schedule`/`workflow_dispatch` и хватит ли 30 минут таймаута на полный клон +
скан в раннере.

**Что нужно сделать после мержа** (тому, у кого есть доступ к GitHub):
запустить джоб вручную (Actions → CI → Run workflow) и убедиться, что
`secrets-history` отработал, в логе есть строка `Находок в истории: 800`
(или другое число), и артефакт `gitleaks-history-report` приложен. До этого
задачу закрывать нельзя — иначе мы получим ровно тот зелёный гейт, который
ничего не проверил.

**2. Разбор 800 находок не делался.** Это отдельная задача; без неё шаг
останется отчётным навсегда.

**3. Ротация утёкшего не делалась** — `AI-46`, `blocked`, `prod-risk`.

**4. Расписание выбрано еженедельным** (пн 03:00 UTC) без согласования — история
меняется медленно. Если нужно чаще/реже, это одна строка в `on.schedule`.
