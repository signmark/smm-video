## 2. По пунктам §11 — что сделано и где

Пункты взяты из `docs/followups/2026-07-24-security-backlog.md`, §11.

**п.1 `npm install` → `npm ci` (lockfile-driven).** `Dockerfile`, обе стадии.
Было `npm install` в builder и `npm install --omit=dev` в runtime — обе
игнорируют lockfile и могут разрешить дерево иначе, чем зафиксировано.
Стало `npm ci` и `npm ci --omit=dev`.

**п.2 Классификация зависимостей / доустановка двух пакетов.** `Dockerfile`,
стадия 2. Было: после `npm install --omit=dev` вторая команда
`npm install @ffmpeg-installer/ffmpeg @ffprobe-installer/ffprobe --omit=dev`
поверх готового production-дерева — она правит `package.json`/`package-lock.json`
прямо в образе, то есть образ собирается не из того манифеста, что в git.
Удалена. Проверено, что она была избыточна: оба пакета лежат в `dependencies`
(`package.json:54-55`), `npm ci --omit=dev` ставит их сам.

Отдельно проверена сама классификация, потому что в описании задачи она указана
как сломанная: **на текущем main она корректна**. Все сборочные инструменты
(`vite`, `esbuild`, `typescript`, `tsx`, `@vitejs/plugin-react`, `tailwindcss`,
`autoprefixer`, `postcss`, `vitest`, `@playwright/test`) лежат в
`devDependencies`; `npm ci` даёт 1668 пакетов, `npm ci --omit=dev` — 1220.
Правок здесь не потребовалось.

**п.3 BuildKit cache.** `Dockerfile`, обе стадии:
`RUN --mount=type=cache,target=/root/.npm npm ci ...`. На результат не влияет —
состав дерева задаёт lockfile, кеш экономит только скачивание (доказательство —
п.3 «Чем доказано» ниже: сборка с кешем и сборка `--no-cache` дали одинаковое
дерево).

**п.4 Dependency audit.** `package.json` → скрипт `audit:prod`
(`npm audit --omit=dev --audit-level=high`) + шаг в `.github/workflows/ci.yml`.
Шаг **отчётный** (`continue-on-error: true`) — см. «что НЕ сделано», п.2.

**п.5 SBOM.** `package.json` → скрипт `sbom`
(`npm sbom --sbom-format cyclonedx --omit=dev`) + шаг в CI с выгрузкой артефакта
`sbom-cyclonedx`. Формат CycloneDX 1.5, 993 компонента.
Важно для ревьюера: `npm sbom` требует **полностью установленного** дерева и
падает с `ESBOMPROBLEMS` на `node_modules`, поставленных через `--omit=dev`.
Поэтому шаг стоит после `npm ci` (полного), а фильтрация прода — флагом
`--omit=dev`, а не частичной установкой.

**Сверх списка §11 — главная находка.** База была `FROM node:22-alpine` —
**плавающий тег**. Даже с `npm ci` пересборка того же коммита через месяц дала
бы другой образ: тег переезжает на новый patch Node. Это прямо ломает критерий
приёмки «одинаковый коммит даёт одинаковый образ». Обе стадии закреплены по
digest `node@sha256:c610fcdfb1d5b4740dd70c284ed3cb16bb857e0f7166196e36a5501df7a3aa32`
(= node v22.23.2 / npm 10.9.8, то же, что тег отдавал на 04.08 — поведение прода
не изменилось).

## 3. Чем доказано

Готовых тестов на Dockerfile в проекте нет, поэтому доказательство —
воспроизводимые прогоны на проде, а не «покрыто тестами».

**Дерево зависимостей детерминировано.** Две независимые сборки:
`build1` (с кешем) и `build2` (`--no-cache`). Список пакетов в
`node_modules` образа — `diff` пустой. Хеш полного списка `имя@версия`
(включая scoped) совпал: `d5dc97fdd27453483c299e143456f41e` у обеих.

**Регрессии относительно текущего прода нет.** Сравнение нового образа с
работающим `root-smm:deployed`: `node_modules` — 731 запись верхнего уровня и
69 scope-каталогов в обоих, `diff` списков пустой; `dist` — 108 файлов,
одинаковый md5 списка. То есть удаление второй `install` и переход на `npm ci`
дали **то же самое** production-дерево, что и раньше.

**Удалённая доустановка действительно не нужна.** Внутри собранного образа:
`require(@ffmpeg-installer/ffmpeg).path` →
`/app/node_modules/@ffmpeg-installer/linux-x64/ffmpeg`,
`require(@ffprobe-installer/ffprobe).path` →
`/app/node_modules/@ffprobe-installer/linux-x64/ffprobe`.

**Lockfile в порядке.** `npm ci --dry-run` проходит без правок lockfile —
второй критерий приёмки выполнен.

## 5. Что НЕ сделано и почему

**1. Побитовая воспроизводимость образа НЕ достигнута.** Одинаковое дерево
зависимостей — да, одинаковый digest образа — нет: `build1` дал
`sha256:1952e942…`, `build2` — `sha256:b35b9cca…`. Причина не в зависимостях, а
в метках времени слоёв. Для побитовой нужен `SOURCE_DATE_EPOCH` +
`--output type=docker,rewrite-timestamp=true` и проверка, что деплой-скрипт с
этим совместим. Считаю это отдельной задачей: критерий «одинаковый коммит даёт
одинаковый образ» сейчас выполнен в смысле «одинаковый состав», но не «одинаковый
хеш», и это расхождение лучше закрыть осознанно, чем протащить молча.

**2. Аудит НЕ блокирующий (`continue-on-error: true`).** В production-дереве уже
22 находки, 13 из них high (в т.ч. `xlsx` — prototype pollution и ReDoS, помечено
`No fix available`). Они существуют на main до этой правки. Блокирующий гейт
покрасил бы CI всем и сразу, включая чужие ветки, и не дал бы ничего починить.
Снимать `continue-on-error` нужно **после** разбора находок — это отдельная
задача в Security & Access, я её не заводил, жду решения владельца.

**3. Дрейф версии Node между CI и образом НЕ трогал.** `.nvmrc` = `20.19.3`,
CI `node-version: 20`, Dockerfile = Node 22. Комментарий в `ci.yml` при этом
утверждает «та же мажорная версия, что в Dockerfile и .nvmrc» — это уже неправда.
То есть тесты и типы гоняются на Node 20, а прод работает на Node 22. Менять
версию в одиночку не стал: это меняет то, на чём реально исполняется прод, и
решение за владельцем. **Рекомендую отдельную задачу.**

**4. Строки `sed` по `package-lock.json` оставлены как есть.** Они заменяют
Replit-реестр на публичный npm. Сейчас это no-op: в lockfile 0 вхождений
`package-firewall.replit.local`. Удалять не стал — минимальный диф и страховка
для репозитория с Replit-историей.

**5. Деплой НЕ выполнялся.** Образ собран и проверен, но контейнер не
переключался, `scripts/deploy-smm.sh` не запускался, `origin/main` не двигался.
По регламенту закрывать AI-42 нельзя, пока правка не выкачена и не проверена на
проде — жду ревью и отмашки.
