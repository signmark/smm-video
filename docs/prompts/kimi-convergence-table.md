# Task: таблица «кто кого вызывает» для конвергенции иерархий платформ

## Context

Working in `G:\Projects\smm-video` (Node.js + TypeScript + Express + Directus + Vitest).

В проекте живут **две параллельные иерархии** platform-сервисов:

- `server/services/social/` (8 файлов): `base-service.ts`, `facebook.ts`,
  `instagram-service.ts`, `telegram-proxy-service.ts`, `telegram-s3-integration.ts`,
  `telegram-service.ts`, `vk-service.ts`, `index.ts`.
- `server/services/social-platforms/` (14 файлов): `base-service.ts`,
  `facebook-service.ts`, `instagram-reels-service.ts`, `instagram-service.ts`,
  `instagram-stories-service.ts`, `telegram-service.ts`, `threads-service.ts`,
  `tiktok-service.ts`, `vk-clips-service.ts`, `vk-service.ts`,
  `vk-stories-service.ts`, `youtube-service.ts`, `youtube-shorts-service.ts`,
  `youtube-video-service.ts`.

Дублируются как минимум `base-service.ts`, `facebook`, `instagram-service.ts`,
`telegram-service.ts`, `vk-service.ts` (по 5 файлов). Тонкая разница в
именовании (`facebook.ts` vs `facebook-service.ts`) не помогает — сути
не меняет, но искать и сравнивать тяжело.

Каждый агент, приходящий чинить баг, берёт ту копию, которую нашёл
первой. Уже были случаи, когда зверь трогал только одну иерархию, потому
что вторая ему не попалась. **Рассинхрон неизбежен**, пока иерархий две.

Эта задача — **чистый анализ**, без правок кода. Цель — дать следующему
витку (будущему исполнителю реальной конвергенции) карту, по которой
планировать слияние: что с чем сталкивается, кто кого дублирует, какие
роуты на какую иерархию завязаны, и в каком порядке их можно безопасно
свести к одной.

## What to do

### Шаг 1. Дупликаты внутри иерархий

Для каждого файла, имя которого встречается в обеих иерархиях (`base-service`,
`facebook`, `instagram-service`, `telegram-service`, `vk-service`), сравни
публичную поверхность (экспортируемые классы и функции) и зафиксируй:

- **одинаковая** публичная поверхность → можно удалить одну из копий
  без последствий (но всё равно см. шаг 3 — кто её зовёт)
- **расходящаяся** публичная поверхность → раздвоенный API, конвергенция
  требует ручного merge интерфейсов
- **один экспортирует, другой нет** → нужно понять, вторая копия реально
  нужна или это dead code

Сравнение должно быть по сигнатурам методов, не по телу (тела могут
расходиться из-за разных мелких правок, но публичный контракт обычно
стабильнее).

### Шаг 2. Карта вызовов «кто кого зовёт»

Собрать два списка импортов:

- Файлы, импортирующие из `services/social/` (например, `import ... from
  '../services/social'` или `'../services/social/telegram-service'`).
  Уже найдено при предварительном сканировании: `server/api/publishing-routes.ts`,
  `server/api/clips-publishing-router.ts`, `server/services/publish-scheduler.ts`
  (через `./social/index`), `server/__tests__/publish-scheduler-routing.test.ts`,
  `server/__tests__/CONTENT_GENERATION_AND_PUBLISHING.test.ts`. Проверить
  свежим `git grep` — могли появиться новые.
- Файлы, импортирующие из `services/social-platforms/` (22 файла, см.
  шапку). Те же — свежим grep'ом.

Для каждой пары «файл → иерархия» отметить, что именно импортируется
(конкретный сервис или фасад `index`). Особое внимание — `social/index`:
его роль как фасада и кто его зовёт (это центральная точка миграции).

### Шаг 3. Карта «что куда добавлять»

Если новая фича (например, новый тип stories) — куда идёт, в `social/` или
в `social-platforms/`? Проверить по истории: `telegram-stories` (если есть)
и `vk-stories` — где живут. Если только в одной иерархии — зафиксировать,
что иерархия «нового типа» де-факто уже определена, и конвергенция = старую
добить до новой.

### Шаг 4. Таблица и план

Свести в **одну markdown-таблицу** со столбцами:

| Файл / Сервис | Иерархия | Кто зовёт (роуты) | Дубль в другой иерархии | Статус дубли | Рекомендация |

Где «Рекомендация» ∈ { «удалить дубль после переноса вызовов», «требует
ручного merge API», «уникален — оставить», «фасад — мигрировать на
него» }.

И отдельной секцией — **предлагаемый порядок миграции** (какой сервис
сводить первым, какой последним; что безопасно сделать одним коммитом;
что требует feature flag или обе параллельные версии на цикл).

## Артефакт

Сохрани результат в **`docs/platform-convergence-table.md`** (новый файл,
в `docs/`, не в `docs/prompts/`). Это будущая опорная точка для
следующего исполнителя.

Формат: заголовок, явная дата (сегодня), статус «черновик анализа —
требует ревью владельца перед merge в основную ветку работ», затем
таблица, затем секция «Порядок миграции», затем открытые вопросы
(если нашёл неоднозначности — вынеси сюда, не додумывай).

## Acceptance criteria

1. `docs/platform-convergence-table.md` создан, имеет дату и явный
   статус «черновик».
2. Таблица покрывает **все 8 файлов `social/`** и **все 14 файлов
   `social-platforms/`** (никаких «TBD» без указания почему).
3. Каждая строка с дубликатом содержит явный вердикт: «одинаковый
   API» / «расходящийся API» / «один экспортирует, другой нет».
4. Список «кто зовёт» собран **свежим `git grep`** на момент
   написания, не по памяти.
5. Секция «Порядок миграции» содержит хотя бы 3 конкретных шага с
   приоритетами (что первое, что последнее, что под feature flag).
6. Открытые вопросы вынесены отдельной секцией; ничего не додумано
   молча.
7. Файл закоммичен с message вида
   `docs(platform-convergence): initial analysis — кто кого зовёт (Kimi)`.
8. Коммит НЕ содержит изменений в коде (`server/`, `client/`, `shared/`).
   Только новый файл в `docs/`.

## Out of scope

- **Не** править ничего в `server/services/social/` или
  `server/services/social-platforms/`. Анализ, не код.
- **Не** трогать тесты. Тесты могут показывать разные имена из-за
  разных иерархий — это и есть один из входов в таблицу, но сами
  тесты не править.
- **Не** пытаться сделать merge или свести две иерархии в одну.
  Это будет следующая задача, после того как владелец утвердит план.
- **Не** править `docs/prompts/`. Артефакт идёт в `docs/`, не в
  `docs/prompts/`.
- **Не** пушить в `origin/main`. Владелец пушит сам.

## DO NOT FIX (conscious trade-offs)

- Само наличие двух иерархий **не** баг. Это исторически сложилось,
  и до утверждённого плана конвергенции — статус-кво. Не
  «улучшай» код, не предлагай «а давайте прямо сейчас сольём».
- `aggressiveTagFixer` НЕ возвращать (удалён в `299becb`).
- DO NOT FIX секции из `review-follow-ups-2026-07-19.md` и
  `review-follow-ups-2026-07-20.md` остаются в силе. Особенно
  для `getContentPublicationStatus` / `published_at = null` для
  partial / `hasScraperData` — это всё трейд-оффы, не предмет
  рефакторинга.
- Текущий план — анализ, не правка. Не предлагай «а заодно
  поправим вот это» мимо задачи.

## Как отчитаться

В ответе дай:
1. Список файлов, у которых обнаружен дубль (с вердиктом по API).
2. Список файлов, которые ни разу ниоткуда не импортируются (если
   такие есть — dead code кандидаты).
3. Сводку «кто зовёт»: для каждой иерархии — список вызывающих
   файлов с количеством вызовов.
4. Топ-3 риска при слепом merge (если бы просто взяли и заменили
   `social/` на `social-platforms/` без подготовки).
5. Хеш коммита с таблицей.
6. Сообщи, если нашёл что-то, что требует внимания **прямо сейчас**
   (баг, security issue, риск потери данных) — отдельным сообщением,
   не в отчёте.
