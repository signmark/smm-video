## 3. Нагрузка

Генератор — `loadtest.mjs` в скретчпаде, без зависимостей, ступени по конкурентности 1→100,
12 с на ступень. **Важная оговорка:** генератор крутится на том же хосте, что и прод, поэтому

конкурирует с приложением. Смотреть надо на форму кривой и на отсутствие 5xx, не на абсолютный rps.

## 4. Находки

### F-1 (P1). Межарендная утечка: чужие источники, тренды и ключевые слова

**Самое серьёзное за прогон.** Свежезарегистрированный аккаунт без единой своей кампании
(`GET /api/campaigns` → `{"data":[]}`) читает данные других пользователей.

Точка входа — `GET /api/sources` **вообще без параметров**:

```bash
curl -s -H "Authorization: Bearer $QA_TOKEN" https://smm.omemo.tech/api/sources
```

→ `HTTP 200`, 523 КБ, **1000 записей из 20 чужих кампаний** (в выдаче — реальные сторонние
бизнесы: клиники, автосалоны, застройщики). Причина: [analytics.ts:190](../../server/routes/analytics.ts#L190)
— фильтр по `campaign_id` навешивается, только если `campaignId` пришёл в query; фильтра по
пользователю нет вообще, стоит просто `limit: 1000`.

Выдача содержит `campaign_id`, то есть отдаёт ключи для второго шага:

| Запрос | Ответ под чужим аккаунтом |
|---|---|
| `GET /api/campaign-trends?campaignId=<чужой>` | 200, **5.5 МБ**, 1694 записи |
| `GET /api/keywords?campaignId=<чужой>` | 200, 11.6 КБ, весь список |
| `GET /api/keywords/<чужой campaignId>` | 200, то же самое |

Цепочка целиком: зарегистрироваться → `GET /api/sources` → собрать все `campaign_id` →
выгрузить по каждому тренды и ключевые слова. Регистрация открыта, ничего угадывать не нужно.

**Почему это именно упущение, а не задумка.** В проекте есть готовый хелпер
[`authorizeCampaignAccess`](../../server/services/campaign-access.ts#L12), и его используют 18 файлов.
Соседние роуты ведут себя правильно и на том же чужом `campaignId` отвечают отказом:

| Роут | Ответ | |
|---|---|---|
| `GET /api/campaigns/<чужой id>` | 404 `Campaign not found` | ✅ |
| `GET /api/campaign-content?campaignId=<чужой>` | 200, `data: []` (фильтр по `user_id`) | ✅ |
| `GET /api/proxy/trends?campaign_id=<чужой>` | 403 `Access denied` | ✅ |
| `GET /api/analytics/top-posts?campaignId=<чужой>` | 404 `CAMPAIGN_NOT_FOUND` | ✅ |

Течёт ровно три роута, которые хелпер не вызывают.

**Важный нюанс для фикса — дырка двухслойная.** `/api/keywords` и `/api/sources` ходят в
Directus **токеном самого пользователя**, и Directus эти строки отдаёт. Значит роль
`SMM Manager User` имеет право читать `campaign_content_sources` и `campaign_keywords`
целиком, без построчного ограничения. Поэтому фильтра в Express мало: нужно и починить роуты,
и урезать права роли в Directus, иначе тот же доступ останется через прямые запросы к Directus.
`/api/campaign-trends` — отдельный случай: он ходит **админским токеном**
([analytics.ts:318](../../server/routes/analytics.ts#L318)), там прав пользователя вообще нет
в уравнении, и защитить может только проверка в коде.

### F-2 (P2). `/api/campaign-trends` игнорирует `limit` и отдаёт 5.5 МБ

Проверено на проде — размер ответа не меняется вообще:

| `limit` | ответ |
|---|---|
| не задан | 5 586 512 Б, 1694 записи |
| `1` | 5 586 512 Б, 1694 записи |
| `5` | 5 586 512 Б, 1694 записи |
| `all` | 5 586 512 Б, 1694 записи |

Разбор задеплоенного бандла (`docker cp smm:/app/dist/server/index.js`) показывает, почему:
в проде у обработчика `const { campaignId } = req.query` — параметры `period` и `limit` не
читаются вовсе, а в Directus уходит захардкоженный `limit: -1` и `fields: "*"`.

Отдельно: `fields: "*"` тянет `raw_source_data` — полный сырой JSON исходного поста. Сервер
использует его только чтобы достать дату публикации (`extractPostDate`), после чего всё равно
отправляет клиенту целиком. Это и есть основная масса пятимегабайтного ответа.

**Осторожно, тут легко ошибиться в диагнозе** (я сам сначала ошибся): в рабочем дереве
`server/routes/analytics.ts` уже лежит незакоммиченная реализация с `limit`/`period`
(`DEFAULT_TRENDS_LIMIT = 500`, `MAX_TRENDS_LIMIT = 5000`, фильтр по `postDate`). Если читать
файл с диска, кажется, что всё починено. На проде этого кода нет — он не закоммичен.
Коммит `2500bf0ea perf(trends)` в истории есть, но он про клиентские фризы, а не про размер ответа.

### F-4 (P3). `GET /api/keywords/search` → 500 вместо 404

`search` и `analyze-website` — это POST-роуты ([ai.ts:423](../../server/routes/ai.ts#L423)).
GET по тем же путям проваливается в `app.get("/api/keywords/:campaignId")`
([campaigns.ts:371](../../server/routes/campaigns.ts#L371)) с `campaignId = "search"` и падает в
500 «Не удалось загрузить ключевые слова». Ожидается 404 или 405. Влияния на пользователей нет,
но 500 шумит в мониторинге и маскирует настоящие ошибки.

### F-5 (P2). Нестроковый `title` роняет создание и правку контента в 500

```bash
curl -s -X POST https://smm.omemo.tech/api/campaign-content \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"campaignId":"<свой id>","title":999,"content":"x"}'
```

→ `HTTP 500 {"error":"Failed to create content","details":"data.title.charAt is not a function"}`

То же с `"title":[1,2]`; `PATCH /api/campaign-content/:id` с `{"title":777}` → 500.
Причина — [content.ts:406](../../server/routes/content.ts#L406): `data.title.charAt(0)` вызывается
без проверки типа; тот же паттерн в PATCH и PUT. Ожидается 400 с валидационной ошибкой.
Побочно: поле `details` выносит наружу сырой текст JS-исключения.

### F-6 (P3). `GET /api/campaign-content/:id` → 500 вместо 404

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  https://smm.omemo.tech/api/campaign-content/00000000-0000-0000-0000-000000000000
```

→ `HTTP 500 {"error":"Failed to fetch content item"}`. Проверено мной лично, повторяется.
Причина — [content.ts:261](../../server/routes/content.ts#L261): общий `catch` превращает любую
ошибку Directus, включая 403 и 404, в 500. Данные при этом не утекают, страдает только код ответа.

### F-7 (P3). `/api/auth/me` отдаёт `unknown@email.com`

Проверено мной лично, два разных эндпоинта на одном и том же токене:

```
GET /api/auth/me       → {"email":"unknown@email.com","first_name":"","last_name":"", ...}
GET /api/user/profile  → {"email":"smmniap+claude-qa@gmail.com","first_name":"Claude", ...}
```

Причина — [auth-routes.ts:521](../../server/api/auth-routes.ts#L521): payload берётся base64-декодом
JWT **без проверки подписи**, а в токене логина полей `email`/`first_name` нет, поэтому
подставляется заглушка. Любой участок UI, берущий имя или почту из `/api/auth/me`, покажет
`unknown@email.com`.

Отдельно проговорю, потому что выглядит страшнее, чем есть: **это не обход авторизации.**
Боевые маршруты идут через `authenticateUser`, который валидирует токен апстримом в Directus
(`/users/me`), а `isAdmin` в этом же ответе считается отдельным авторитетным запросом
со static-токеном. Подделанный токен на защищённых маршрутах отклоняется. Проблема — только
в том, что отображаемые поля берутся из неверифицированного источника, где их попросту нет.

### F-8 (P2). У 340 из 845 «опубликованных» постов нет даты публикации

Прошёлся по всем 1422 записям контента владельца. Разбивка по статусам:

| статус | штук |
|---|---|
| `published` | 845 |
| `draft` | 427 |
| `partially_published` | 122 |
| `partial` | 22 |
| `error` | 3 |
| `scheduled` | 1 |
| `publishing` | 1 |
| `dreft` | 1 |

**У 340 записей со статусом `published` поле `published_at` пустое** — это 40% всех
опубликованных. Проверил не только режим сводки, но и полную форму записи через
`GET /api/campaign-content/:id`: там `published_at: null` тоже, то есть это не артефакт
маппинга, а реальное состояние базы.

Почему это важно именно сейчас: любой отчёт или график, который группирует по дате
публикации, эти 340 записей молча теряет. Под это подпадают «График активности за последние
30 дней» на дашборде и экспорт отчётов, который только что правили в `760ad1fed`. Цифра
«всего опубликовано» при этом верная — расходятся именно разрезы по времени.

Причину я не искал — это уже работа для разработчика. Вопрос в том, где теряется установка
`published_at` при публикации, и надо ли разово досчитать историю (например, из
`social_platforms` или из `date_updated`).

### F-10 (P2). `GET /api/campaign-content/:id` отдаёт форму, отличную от списка

Список ([content.ts:135](../../server/routes/content.ts#L135)) приводит запись к camelCase и
разбирает массивы через `parseArrayField`. Одиночный эндпоинт
([content.ts:457](../../server/routes/content.ts#L457)) отдаёт **сырую строку Directus как есть**:

```js
const response = await directusApi.get(`/items/campaign_content/${id}`, ...);
res.json({ data: response.data.data });   // без маппинга
```

Проверено на живой записи: в списке приходит `publishedAt`, по `:id` — `published_at`,
а `publishedAt` отсутствует. То же будет с `campaignId`/`campaign_id`, `imageUrl`/`image_url`
и с полями `keywords`/`hashtags`/`links`, которые в списке распарсены в массивы, а здесь
приедут строкой.

Отмечаю отдельно, потому что это прямо ломает предложенный план оптимизации страницы
«Контент»: там предлагалось дотягивать полный объект для диалога редактирования именно через
`GET /:id`. В нынешнем виде диалог получит поля не под теми именами. Эндпоинт надо сперва
привести к форме списка (и заодно починить F-6 — там же стоит общий `catch` в 500).

### Почему фильтровать по `user_id` было нельзя

Ключевой вопрос оказался с неочевидным ответом. У `campaign_content_sources` колонка `user_id`
в схеме есть, но **её не пишет ни один путь создания** — ни `POST /api/sources`, ни
`trend-collector`, ни `telegram-channels-routes`, ни `autonomous-ai`. У `campaign_keywords`
такой колонки нет вовсе. Фильтр по `user_id` ночью опустошил бы владельцу списки источников
и ключевых слов. Принадлежность считается только через `user_campaigns`.

### Регрессия, которую поймал только прогон по проду

После первой выкатки фикса `GET /api/sources` и `GET /api/trends` стали отдавать **503**
любому неадмину — даже когда своя кампания у него есть. Тесты при этом были зелёные.

Причина: `listAccessibleCampaignIds` фильтровал по `_or[user_id, user_created]`, а живой
Directus отвергает это с 403 — «no permission to access field `user_created` in collection
`user_campaigns` or it does not exist». В SQL-схеме колонка есть, но у роли поля нет.
Fail-closed `catch` превращал 403 в 503.

Мок Directus такое поймать не мог в принципе, и тест дополнительно фиксировал именно
отвергаемую форму фильтра — то есть закреплял поломку. Исправлено в `f69783ec5`: фильтр
только по `user_id`, как в каноническом `GET /api/campaigns`; тест переписан.

**Вывод на будущее:** тесты с моком Directus проверяют форму запроса, а не то, что живой
Directus её примет. Для путей, где меняется фильтр или набор полей, нужен прогон по проду.

### F-12 (P3). Ссылка сброса пароля не одноразовая

[password-reset.ts:7](../../server/api/password-reset.ts#L7): токен — это чистый
`HMAC(userId:ts)`, серверного состояния нет. Отсюда следствия:

- **смена пароля не гасит ссылку** — она остаётся рабочей весь час;
- одной и той же ссылкой можно воспользоваться сколько угодно раз в пределах TTL.

Сценарий, где это стреляет: пользователь сбросил пароль, письмо осталось в почте (переслано,
общий ящик, утечка почты) — в течение часа по нему пароль меняется снова. Отраслевая норма —
одноразовый токен, гасящийся при использовании и при любой смене пароля.

Рядом, помельче, из того же файла:

- **сравнение токенов не константное по времени** ([:97](../../server/api/password-reset.ts#L97),
  обычный `!==`). Практически по сети эксплуатировать тяжело, но правильный ответ —
  `crypto.timingSafeEqual`;
- **захардкоженный запасной секрет** `'smm-reset-secret'`
  ([:8](../../server/api/password-reset.ts#L8)). Сейчас не стреляет: если админского токена нет,
  подтверждение всё равно упадёт в 500 раньше. Но это мина — при другом порядке проверок
  публичная строка из репозитория становится ключом подписи токенов сброса;
- **пользователю не приходит письмо о том, что пароль сменили** — то есть чужой сброс проходит незаметно.

### Проверено, и здесь всё в порядке

- **Инъекция через заголовок `Host` не проходит.** `getBaseUrl`
  ([:12](../../server/api/password-reset.ts#L12)) строит ссылку сброса из `req.get('host')` —
  это классический вектор увода токена: подставил свой Host, письмо ушло настоящему
  пользователю, а ссылка в нём ведёт на домен атакующего. **Но не эксплуатируется:** traefik
  маршрутизирует по домену и отдаёт 404 на любой чужой Host (проверил с `evil.replit.dev` и
  `attacker.roboflow.space`). Подмена через `X-Forwarded-Host` тоже не работает: код читает
  именно `req.get('host')`, который в Express возвращает сырой заголовок и на `trust proxy`
  не реагирует.

  Записываю как скрытый риск, а не как дыру: защищает инфраструктура, а не код. Стоит выкинуть
  вычисление базового URL из заголовка и брать его из переменной окружения.
- **Существование аккаунта не раскрывается** — на несуществующий email тот же `{"success":true}`.
- **Валидация подтверждения сброса держит мусор:** пустое тело, подделанный токен, короткий
  пароль, протухший и будущий `ts`, `userId` объектом, пароль числом — везде 400 с внятным
  текстом, ни одной 500.
- Сброс и регистрация под `sensitiveLimiter` (20 попыток за 15 минут).

## 8. Четвёртый заход: даты публикации, одноразовый сброс, 405

Выкачено `f807964ed`, `814516471`, `a549dfb46` (плюс параллельные `1611c6dbd`, `d183979fc`).
Точка отката — образ `root-smm:rollback-before-2012`.

### F-8: причина найдена, история досчитана НЕ будет

Корень — в [shared/schedule-time.ts](../../shared/schedule-time.ts): `isConfirmedPublishedPlatform`
считает платформу опубликованной по `postId`/`postUrl` **даже без** `publishedAt`, а
`getContentAggregateTimes` собирает дату **только** из `publishedAt`. То есть если n8n записал
платформу с `postUrl`, но без даты, статус контента становится `published`, а дата остаётся пустой.
В publish-now дыра была закрыта хелпером `resolvePublishFinalization`, остальные пути его не звали.

Три пути записи, все чинились:

1. `publish-scheduler.ts` — основной по объёму, шёл мимо хелпера;
2. `publishing-routes.ts` (`mark-as-published`) — статус писался через storage, а дата отдельным
   запросом под токеном **случайной активной сессии**; нет сессий → токен `null` → дата не ставилась,
   ошибка глушилась;
3. `social-platform-status-webhook.ts` — подстраховочный PATCH слал camelCase `publishedAt`,
   которого в таблице нет, из-за чего Directus отбивал **весь** запрос и статус не обновлялся вовсе.

**Историю решено не досчитывать, и я с этим согласен.** Восстановить дату можно только там, где
хотя бы одна платформа в `social_platforms` несёт свой `publishedAt`. Где не несёт ни одна —
честного источника нет: `date_updated` это время любой последней правки (редактирование текста,
пересчёт статуса, миграция), и подстановка нарисовала бы в графике активности ложные всплески
в дни, когда ничего не публиковалось. Молчаливый пропуск лучше правдоподобной выдумки.

Скрипт `scripts/maintenance/backfill-published-at.ts` положен, **на проде не запускался**.
По умолчанию dry-run, запись только по `--apply`, трогает исключительно восстановимую часть.

### F-12: ссылка сброса стала одноразовой

Гасится при использовании (до обращения к Directus, поэтому повтор не доходит до смены пароля),
при любой смене пароля — включая смену из профиля, — и при выдаче новой ссылки. Добавлены
`crypto.timingSafeEqual`, письмо-уведомление о смене пароля; убран запасной секрет
`'smm-reset-secret'`.

**Компромисс, о котором надо знать:** хранилище — `Map` в памяти процесса. Рестарт контейнера
гасит все выданные ссылки, и пользователю придётся запросить письмо заново. Это fail-closed
(рестарт ссылку гасит, а не воскрешает), но при деплое в момент, когда кто-то сбрасывает
пароль, он увидит «недействительная ссылка». При нескольких инстансах ссылка будет валидна
только на выдавшем — сейчас инстанс один.

Отдельно проверил после выкатки, что удаление запасного секрета ничего не сломало: запрос
сброса и на несуществующий, и на реальный адрес отвечает 200 без ошибок в логе, то есть путь
подписи токена и отправки письма отработал. `timingSafeEqual` не падает на токенах разной длины
(1, 8 и 40 символов — везде 400).

### F-4: 405 вместо 500

`GET`, `DELETE`, `PUT` на `/api/keywords/search` и `/api/keywords/analyze-website` теперь дают
**405** с заголовком `Allow: POST`. Настоящие идентификаторы кампаний обслуживаются как прежде
(чужой → 404 от проверки доступа).

### Мутационная проверка — важная деталь

Возврат `!==` вместо `crypto.timingSafeEqual` **мутацию сначала пережил**: постоянство времени
поведением не отличимо, обычный тест его не ловит. Добавлен структурный тест, оборачивающий
реальный `crypto.timingSafeEqual`. Это стоит запомнить: у защиты от тайминга нет наблюдаемого
поведения, и проверять её надо иначе, чем остальную логику.

Тестов стало **1260** (было 1161), 114 файлов. `npm run check` чист.

## 9. Риск захвата админского аккаунта через утраченный почтовый ящик

Владелец сообщил, что **не имеет доступа к почте, на которую заведён его основной админский
аккаунт**: ящик использовался командой и остался у человека, который из команды ушёл.

### Почему это горит

Восстановление пароля отправляет ссылку на почту аккаунта. Значит тот, у кого остался доступ
к ящику, **в любой момент забирает админский аккаунт**: запрашивает сброс, получает письмо,
задаёт свой пароль. Дальше у него права `is_smm_admin` — то есть доступ к списку всех 97
пользователей, к их тарифам и срокам, и к админским эндпоинтам. Механизм сброса, который
я этой ночью укреплял (одноразовая ссылка, `timingSafeEqual`, уведомление о смене), работает
корректно — и ровно поэтому он честно отработает на владельца ящика.

Обратная сторона: **владелец сам не может воспользоваться восстановлением пароля** для своего
основного аккаунта.

### Хорошая новость: чинится из интерфейса, без Directus

`PUT /api/user/profile` ([user.ts:74](../../server/routes/user.ts#L74)) передаёт новый `email`
в Directus. То есть почту аккаунта можно сменить на подконтрольную прямо со страницы профиля.

Админка дополнительно умеет `PATCH /admin/users/:userId`
([admin-users.ts:120](../../server/routes/admin-users.ts#L120)) с полями `is_smm_admin`,
`status`, `plan`, `expire_date` — то есть снять админские права и перевести аккаунт
в `suspended`. Смены чужой почты там нет.

**Никаких действий с аккаунтами я не предпринимал** — это решение владельца, и ошибиться тут
дорого.

### F-14 (P2). Смена почты и пароля в профиле не требует подтверждения

Найдено при разборе предыдущего пункта, в том же обработчике
[user.ts:74](../../server/routes/user.ts#L74):

- **новый пароль применяется без ввода текущего** — в теле запроса достаточно `new_password`;
- **новая почта применяется без подтверждения по ссылке** — смена мгновенная.

Следствие: одного украденного токена сессии достаточно, чтобы полностью забрать аккаунт —
поменять пароль, не зная старого, и переписать почту на свою, после чего законный владелец
теряет и вход, и возможность восстановления. Уведомление о смене пароля, добавленное ночью,
уйдёт уже на новый адрес, если атакующий сменит почту первой.

Что надо: запрашивать текущий пароль при смене пароля и почты, а новую почту подтверждать
ссылкой, оставляя старую активной до подтверждения. Уведомление о смене адреса слать на
**старый** адрес.

Отдельно замечу по общей картине: из 97 пользователей **все 97 в статусе `active`**, ни один
не деактивирован. Процесса отключения ушедших людей, судя по этому, нет вовсе.

### F-15 (P2). Одноразовые ссылки не переживают рестарт — и деплои идут одновременно из нескольких сессий

Проверял одноразовость сброса на настоящей ссылке из письма (владелец прислал URL от тестового
аккаунта). Ссылке было **19 минут из 60**, но прод её отверг: `«Ссылка уже использована или
недействительна»`, HTTP 400. Пароль при этом не сменился — старый вход работает, то есть
механизм fail-closed отработал корректно.

Причина, по которой живая ссылка умерла раньше срока: **контейнер перезапустился в 20:37**,
через 14 минут после выдачи ссылки в 20:23. Хранилище одноразовых токенов
([password-reset-tokens.ts](../../server/utils/password-reset-tokens.ts)) — `Map` в памяти
процесса, рестарт стирает все выданные ссылки. Это заявленный компромисс из раздела 8, но он
выстрелил на реальном пользователе в первые полчаса.

Почему был рестарт — отдельная, более тревожная находка: `RestartCount: 0`, `ExitCode: 0`,
не падение. Образ **пересобран в 20:37** и контейнер пересоздан. В истории появились чужие
коммиты после моего `f53bd581d` — `c5683daa0`, `d00ff77de`, `37aebb2a5`, `3f651b9e4` (правки
engagement). То есть **параллельная сессия выкатила свой код на прод**, пока шёл этот прогон.
Деплой сейчас идёт одновременно из нескольких сессий над одним рабочим деревом, и один деплой
незаметно инвалидирует ссылки сброса/подтверждения, выданные к этому моменту.

Для обычного механизма сброса это терпимо. Но в ситуации владельца (см. раздел 9) сброс пароля —
способ вернуть контроль над админкой на утраченном ящике, и окно «запросил письмо → успел
перейти по ссылке» может схлопнуться в любой момент из-за чужого деплоя, без предупреждения.

**Вывод для F-14:** хранилище токенов подтверждения почты и сброса пароля должно переживать
рестарт — коллекция в Directus или таблица, а не `Map` в памяти. Иначе подтверждение смены
почты будет ломаться при каждом деплое ровно так же. Это добавлено в задачу F-14.

### Что удалось и что не удалось проверить по одноразовости

- **Проверено на проде:** недействительная/устаревшая ссылка → 400, смена пароля не происходит,
  старый пароль остаётся рабочим. Fail-closed подтверждён.
- **НЕ проверено end-to-end:** «перешёл по свежей ссылке → сменил пароль → повтор той же ссылкой
  отвергнут». Нужна живая ссылка из письма, дожившая без рестарта контейнера. Добыть токен
  самостоятельно можно только вычислением из секрета подписи — это подделка токена, окружение
  её справедливо заблокировало, обходить не стал. Одноразовость на пути «использована → повтор»
  остаётся подтверждённой только юнит-тестами разработчика.

### F-16 (P3). В письме сброса нет аккаунта и времени, имя не экранировано

Владелец переслал тело письма. В шаблоне
([password-reset.ts:58](../../server/api/password-reset.ts#L58)):

- не указано, **для какого аккаунта** запрошен сброс — при нескольких учётках непонятно, какая;
- нет времени запроса и намёка на источник — человек не может отличить свой запрос от чужого;
- имя подставляется в HTML без экранирования (`<b>${firstName}</b>`). Стреляет слабо (письмо
  уходит на собственный адрес зарегистрировавшегося), но это тот же класс неэкранированной
  интерполяции. Передано в задачу F-14 вместе с остальной доработкой письма.

На фоне раздела 9 первые два пункта перестают быть косметикой: когда чужой сброс — реальный
сценарий, письмо обязано давать человеку понять, его это действие или нет.

## 10. Пятый заход: промокоды и авторизация

### F-17 (P2). Гонка в погашении промокода → бесплатный Pro в обход лимитов

[promo-codes.ts:306](../../server/routes/promo-codes.ts#L306), `POST /api/promo/redeem` —
классический TOCTOU. Порядок: (1) проверка «пользователь уже использовал этот код»
(запрос в `promo_code_uses`), (2) проверка `used_count >= max_uses`, (3) выдача дней/Pro
пользователю, (4) запись факта использования, (5) инкремент `used_count`. Между проверкой (1,2)
и записью (4,5) нет ни транзакции, ни блокировки, ни уникального индекса.

Два следствия при параллельных запросах:

- **Повторное использование одним пользователем.** N одновременных запросов с одним кодом от
  одного аккаунта все проходят проверку (1) до того, как хоть один запишет использование (4).
  Каждый начисляет дни/Pro — то есть код на «30 дней Pro» превращается в N×30 при N параллельных
  запросах.
- **Обход `max_uses`.** `used_count` читается, проверяется и инкрементируется неатомарно —
  пачка одновременных погашений читает одно и то же значение и все проходят лимит.

Финансовое влияние прямое: бесплатный Pro-доступ в обход ограничений промокода. **На проде не
эксплуатировал** — это мутировало бы аккаунт и состояние промокодов, а гонку нельзя проверить,
не забив реальными параллельными запросами. Находка по коду, паттерн однозначный. Не проверено
одно: есть ли на `promo_code_uses` уникальный индекс `(promo_code_id, user_id)` на уровне БД —
если он есть, повторное использование одним пользователем упрётся в него на шаге (4). Обход
`max_uses` он всё равно не закрывает. Это надо проверить на живом Directus и, если индекса нет,
завести; плюс сделать погашение атомарным (условный апдейт `used_count` с проверкой предела,
или блокировка).

### F-18 (P3). Нестроковый код промокода → 500

`POST /api/promo/validate` с `{"code": 12345}` или `{"code": ["A","B"]}` → **500**
`{"error":"Ошибка проверки промокода"}`. Причина — `code.toUpperCase()`
([promo-codes.ts](../../server/routes/promo-codes.ts)) на нестроковом значении. `redeem` разделяет
тот же паттерн (`code.toUpperCase().trim()`), то есть тот же дефект. Тот же класс, что F-5
(нестроковый `title`): нет проверки типа перед строковым методом, ожидается 400. Проверено:
на `validate` воспроизводится стабильно; на `redeem` эмпирически добить не смог (сетевой сэндбокс
режет POST на этот эндпоинт), но код идентичен.

### Проверено, претензий нет

- **Авторизация админских промокодов держится:** `GET`/`POST /api/admin/promo-codes` под обычным
  аккаунтом → 403.
- **Инъекции в код промокода безопасны:** `' OR 1=1 --` и строка на 5000 символов → корректный
  404 «не найден», без 500 и без побочных эффектов.
- Валидация: пустое тело → 400 «Укажите код», несуществующий код → 404.
- QA-аккаунт после всех проб цел: план `trial`, почта на месте — ни одна проба ничего не начислила.

_Замечание по ходу: сетевой сэндбокс сессии периодически режет исходящие (`HTTP 000`,
`time=0`), особенно на POST к `/api/promo/redeem`. Это сторона тестового окружения, не прод —
прод в эти моменты отвечал `/health` 200 и обслуживал владельца. На результаты по коду не влияет._

403/400 у Directus после деплоя — ноль по моей проверке.

**Уточнение по историческому объёму (и признание своей ошибки).** Сначала я не воспроизвёл
довакцинный агрегат соседа и списал это на короткий буфер логов Directus — **это была моя
ошибка в паттерне**, не буфер. Лог `root-directus-1` — 59 МБ без ротации, история глубокая.
Directus пишет отказ как `GET /path 403 9ms`, то есть ловить надо ` 403 ` с пробелами, а не по
слову `Forbidden` (его в логе нет). Исправленным grep воспроизвёл: **265 отказов 403 за 6 часов,
1748 за всё время (с ~10 июля), 0 после деплоя (21:10)**. Честная оговорка, которую подтвердил
и я по путям: часть исторических 403 — **диагностические запросы самих сессий**, не приложение
(в последнем часе — `/items/promo_code_uses`, `/items/content_sources`, `/items/user_api_keys`,
`/items/business_questionnaire`; приложение туда так не ходит). Корректная формулировка:
**403 приложения после деплоя — ноль; исторический объём 1748 за 17 дней включает диагностический
шум сессий.**

Побочно это подтверждает пункт про ротацию: **у самого Directus лог уже 59 МБ и не ротируется** —
«ротации нет ни у одного сервиса» это не гипотеза, а факт с конкретным примером.

Поправка про логгер: `pino` сосед в итоге **не ставил** — весь этап 1 (уровни, `LOG_LEVEL`,
JSON, redact) сделан без новой зависимости. `package.json` не менялся, значит **отдельного
раунда сборки под зависимость не нужно** — логгер уедет обычной пересборкой образа, когда
владелец даст отмашку по ротации и уровню.

**Урок процесса остаётся в силе:** несколько сессий над одним рабочим деревом + любая может
собрать образ = деплой выносит на прод всё, что лежит в дереве. Сработало сегодня только потому,
что удалось скоординироваться вручную (пинги между сессиями, пауза на чистое окно). Это не
масштабируется. Правильное решение — отдельные worktree/ветки на сессию либо один ответственный
за деплой. Записано для владельца отдельным пунктом ниже.

## 12. Логгер соседа готов, но деплой держу — решение за владельцем

Сессия «Ошибки Forbidden в логах» закоммитила переход логов на pino с уровнями
(`30a6a77ab`, тесты 1311 зелёные). Я его **не выкатываю** — тут два действия, оба за пределами
моей роли, и оба требуют владельца.

### Риск, из-за которого нельзя просто выкатить

Логгер расглушает уровни: раньше в проде `log.info` и почти все `error` не печатались вовсе
(печатались только совпадения с 12 русскими фразами + список подавления по подстроке). Теперь
уровень задаёт автор строки, порог из `LOG_LEVEL` (по умолчанию `info`). В коде **3705 вызовов
`log()`, из них с явным уровнем только 329** — остальные ~3376 default `info` и в проде до сих
пор молчали. После деплоя они станут видны. Самые громкие — пути публикации:
`social-publishing.ts` (215), `social/telegram-service.ts` (142), `publishing-routes.ts` (113),
`trends-routes.ts` (92), `publish-scheduler.ts` (69) — десятки строк на одну публикацию.

При этом (проверил сам): **у контейнера `smm` в `/root/docker-compose.yml` нет ротации логов
вообще** — `json-file` с пустым конфигом. Ротации нет ни у одного сервиса (`max-size`: 0).

**Поправка к масштабу риска (важно — первая оценка была завышена).** Сосед пересчитал точнее,
я перепроверил независимо и получил то же: **550 строк / 48 КБ за 14 минут ≈ 5 МБ/сутки** при
текущем уровне. Даже ×10 от путей публикации — ~50 МБ/сутки, ~1,5 ГБ/месяц против 27 ГБ
свободных. Это **вопрос гигиены, а не «диск вот-вот забьётся».** Более того, **55% сегодняшнего
шума логгер вообще не трогает**: `[HTTP]` (221 из 550, 40%) и `[user-auth] fetchAdminStatus`
(84, 15%) идут голым `console.log` мимо логгера; по плану `[HTTP]` станет нормальным access-логом
(этап 2), а `fetchAdminStatus` уедет в debug (этап 5) — то есть после этих этапов объём скорее
упадёт, чем вырастет. Настоящий хвостовой риск — не публикации, а **сорвавшийся цикл**, который
начнёт молотить в лог; вот от него ротация и страхует.

Итог: ротация — правильная гигиена и страховка от runaway-петли, но **не блокер деплоя логгера**.
Я всё равно держу деплой до решения владельца (это его инфраструктура и его выбор уровня), просто
картина рисков честнее, чем в моей первой эскалации.

### Почему держу и не правлю сам

- **Правку `/root/docker-compose.yml` не делаю.** Это конфиг общего прод-стека (traefik,
  postgres, directus, n8n, smm), а не репозиторий. Мне авторизовали деплой кода репозитория,
  не изменение инфраструктуры. Правка того же файла у соседа была заблокирована защитой — тот
  же сигнал. Сосед уже написал владельцу.
- **Логгер не выкатываю.** Это работа соседа, и именно она создаёт риск диска. Выбор
  (ротация + `LOG_LEVEL`) — решение владельца, сосед изложил ему два варианта.
- Текущий прод стабилен: чистый HEAD `37ccb05f7` без логгера, health 200. Держать деплой —
  нулевой риск для прода сейчас.

### Что нужно от владельца

1. Добавить ротацию сервису `smm` в `/root/docker-compose.yml` (сосед предложил
   `max-size: 50m`, `max-file: 5`) — **до** выката логгера. Либо явно разрешить сделать это мне.
2. Выбрать первый заход: (1) ротация + `LOG_LEVEL=info` (видно всё, объём меряем и гасим
   громкие места), или (2) `LOG_LEVEL=warn` (все ошибки/предупреждения, которых в проде не было
   никогда, но теряются 256 `log.info`). Сосед и я — за вариант 1, но только с ротацией.
3. Кто выкатывает логгер (второй раунд, т.к. нужен `npm install pino` → сборка образа).

Как только владелец решит — подстрахую замером объёма (`docker logs smm --since 5m | wc -l`
и разбивка по `source`) и откатом на `root-smm:rollback-2046` при опасном росте.

## 13. Шестой заход: привилегии и платёжный вебхук

### F-20 (P2, безопасность). Вебхук YooKassa доверяет метаданным из тела

Две точки активации подписки, и они **непоследовательны**:

- `POST /api/payments/:paymentId/activate` ([yookassa.ts:196](../../server/routes/yookassa.ts#L196)) —
  **сделано правильно.** Платёж перепроверяется через API YooKassa, а `user_id`/`plan` берутся
  из **проверенного** объекта (`payment.metadata`, где `payment` = ответ YooKassa). Активация
  идёт реальному плательщику; чужой `paymentId` просто пере-активирует его же — атакующему
  бесполезно.
- `POST /api/yookassa/webhook` ([yookassa.ts:276](../../server/routes/yookassa.ts#L276)) —
  **дефект.** `metaUserId`/`metaPlan` берутся из **тела запроса** (`event.object.metadata`),
  а `verified = GET /{paymentId}` проверяет только `status === 'succeeded' && paid`. Привязка
  метаданных к проверенному платежу не проверяется.

**Вектор:** регистрация открыта → атакующий получает токен → шлёт на вебхук поддельное тело
`{event:"payment.succeeded", object:{id:<ID реального оплаченного платежа>, paid:true,
metadata:{user_id:<свой>, plan:"pro"}}}`. Перепроверка проходит (платёж-то настоящий), и
`activateSubscription(<свой>, "pro")` выдаёт Pro. Реальный succeeded `paymentId` берётся из
собственного прошлого платежа (тогда это апгрейд дешёвого тарифа до `pro`) или из любого
утёкшего ID. **YooKassa на проде настроена** (`/api/payments/available` → `available:true`),
то есть путь живой.

**Не эксплуатировал** — подделка платёжных вебхуков это мошенничество и бессмысленный риск.
Находка по коду, паттерн однозначный. Фикс тоже: вебхук должен брать `user_id`/`plan` из
`verified.metadata`, ровно как уже делает `/activate`.

Оговорка по контексту: в памяти проекта отмечено, что строгого энфорсмента оплаты пока нет
(«публичный bypass цен/оплаты, сброс на free при входе»). То есть на фоне и так нестрогого
биллинга практическая ценность дыры сейчас ниже, но паттерн «доверять телу после проверки
только факта оплаты» — конкретный и его надо закрыть до того, как биллинг ужесточат.

### F-21 (P3, функциональность). Вебхук YooKassa за глобальным auth — не примет реальный колбэк

`app.use('/api', yookassaRouter)` монтируется **после** глобального auth-middleware
([index.ts:905](../../server/index.ts#L905)), поэтому `POST /api/yookassa/webhook` без JWT
даёт **401** (проверил на проде). Реальные уведомления YooKassa приходят **без** пользовательского
токена — значит вебхук их отвергает, и авто-активация подписки по вебхуку де-факто не работает.
Оплата активируется только когда клиент после редиректа сам зовёт `/payments/:paymentId/activate`.
Если пользователь закрыл вкладку до опроса success-страницы — подписка может не активироваться.

Ирония: этот же auth-гейт частично прикрывает F-20 от полностью анонимной эксплуатации (нужен
хоть какой-то токен), но не закрывает её (регистрация открыта). Правильно — сделать вебхук
публичным (как VK-webhook, см. память [[smm-facebook-router-global-auth-trap]]) **и одновременно**
чинить F-20, иначе публикация вебхука откроет дыру настежь.

### Проверено, претензий нет

- **Привилегии не поднять:** `PATCH /api/admin/users/:id` под обычным аккаунтом — 403 на всё
  (себе `is_smm_admin=true` → 403, себе `plan=pro` → 403, чужому админу `is_smm_admin=false` →
  403). Права и тариф QA-аккаунта не изменились.
- `/payments/:paymentId/activate` привязывает активацию к проверенному плательщику — не к вызывающему.

### F-1 write-side: пробел закрыт — проверено на проде

В F-1 я оставлял оговорку: запись в чужую кампанию проверить не смог (окружение блокировало
пробу), пометил как «считать подозрительным». Теперь проверил на живом проде под QA-аккаунтом
(0 своих кампаний) против чужого `campaignId` владельца:

| Путь записи | Ответ |
|---|---|
| `POST /api/sources` (источник в чужую кампанию) | **404** |
| `POST /api/keywords/analyze-website` (чужая кампания) | **404** |
| `POST /api/campaigns/:id/keywords` (валидный `url`, чужая кампания) | **404** до AI-вызова |

Нюанс, который проверил отдельно: у `POST /api/campaigns/:id/keywords` проверка `if (!url)`
стоит **раньше** `authorizeCampaignAccess` ([campaigns.ts:501](../../server/routes/campaigns.ts#L501)),
поэтому пустое тело даёт 400 «URL обязателен» до проверки владельца. Это безобидный
шорт-сёркат — записи не происходит, а с валидным `url` управление доходит до проверки владельца
и чужая кампания получает 404 раньше, чем случится AI-вызов или запись. Все четыре пути записи,
которые чинил агент по F-1 (плюс `DELETE /api/keywords/:id`, закрытый тестом ранее), **теперь
подтверждены на проде** — межарендная запись закрыта, не только чтение.

### Заголовки безопасности — отсутствие CSP/X-Frame-Options ОСОЗНАННОЕ (не бага)

Проверил ответы прода: есть HSTS (`max-age=31536000; includeSubDomains`), `x-content-type-options:
nosniff`, `referrer-policy: no-referrer`, `x-xss-protection: 0` (это современная норма — отключить
легаси-аудитор). **Нет** `Content-Security-Policy` и `X-Frame-Options`.

Сначала это выглядело как дыра (кликджекинг: страницу можно встроить в iframe, а на ней — профиль
со сменой пароля/почты). Но в коде это **намеренно и задокументировано**
([index.ts:191](../../server/index.ts#L191)): `helmet({ contentSecurityPolicy: false,
frameguard: false, ... })` — приложение работает как **Telegram Mini App внутри iframe**
`web.telegram.org`, поэтому X-Frame-Options должен быть выключен, иначе Telegram не встроит;
CSP выключен из-за ассетов с S3. Это законная причина, не наивный недосмотр.

Уточнение на будущее (не срочно, задачу не завожу): «должно встраиваться Telegram, но не кем
попало» точнее выражается через CSP `frame-ancestors 'self' https://web.telegram.org
https://*.telegram.org`, а не через полное отключение frameguard — тогда Telegram может, а
произвольный сайт нет, и защита от кликджекинга возвращается. Плюс острота кликджекинга уже
снижена фиксом F-14: смена пароля/почты теперь требует текущий пароль, то есть подсунуть её
кликджекингом не выйдет. Итог: осознанный компромисс, поле для аккуратного улучшения, не дефект.

### Класс «500 на нестроковый ввод» — НЕ системный (проверено)

Трижды за ночь всплывал 500 вместо 400 на мусорный тип (F-5 `title`, F-18 промокод). Прогнал
восемь пользовательских POST мусорными типами (число/массив/объект вместо строки), чтобы понять,
системно ли это:

| Эндпоинт | Результат |
|---|---|
| `POST /api/support/message` (число, массив) | 400 ✓ |
| `POST /api/content/generate-plan` (число) | 400 ✓ |
| `POST /api/keywords` (массив) | 404 (tenant-check раньше) ✓ |

привести `name` к обязательной строке. Мусорную кампанию, созданную пробой, за собой удалил;
QA-аккаунт чист.
