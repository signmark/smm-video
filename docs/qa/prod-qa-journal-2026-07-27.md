## 3. Нагрузка

Генератор — `loadtest.mjs` в скретчпаде, без зависимостей, ступени по конкурентности 1→100,
12 с на ступень. **Важная оговорка:** генератор крутится на том же хосте, что и прод, поэтому
RTT почти нулевой и цифры rps завышены относительно реальных клиентов, а CPU генератора
конкурирует с приложением. Смотреть надо на форму кривой и на отсутствие 5xx, не на абсолютный rps.

## 4. Находки

### F-1 (P1). Межарендная утечка: чужие источники, тренды и ключевые слова

**Самое серьёзное за прогон.** Свежезарегистрированный аккаунт без единой своей кампании
(`GET /api/campaigns` → `{"data":[]}`) читает данные других пользователей.

Точка входа — `GET /api/sources` **вообще без параметров**:

```bash
curl -s -H "Authorization: Bearer $QA_TOKEN" https://smm.omemo.tech/api/sources
```

→ `HTTP 200`, 523 КБ, **1000 записей из 20 чужих кампаний** (в выдаче — реальные сторонние
бизнесы: клиники, автосалоны, застройщики). Причина: [analytics.ts:190](../../server/routes/analytics.ts#L190)
— фильтр по `campaign_id` навешивается, только если `campaignId` пришёл в query; фильтра по
пользователю нет вообще, стоит просто `limit: 1000`.

Выдача содержит `campaign_id`, то есть отдаёт ключи для второго шага:

| Запрос | Ответ под чужим аккаунтом |
|---|---|
| `GET /api/campaign-trends?campaignId=<чужой>` | 200, **5.5 МБ**, 1694 записи |
| `GET /api/keywords?campaignId=<чужой>` | 200, 11.6 КБ, весь список |
| `GET /api/keywords/<чужой campaignId>` | 200, то же самое |

Цепочка целиком: зарегистрироваться → `GET /api/sources` → собрать все `campaign_id` →
выгрузить по каждому тренды и ключевые слова. Регистрация открыта, ничего угадывать не нужно.

**Почему это именно упущение, а не задумка.** В проекте есть готовый хелпер
[`authorizeCampaignAccess`](../../server/services/campaign-access.ts#L12), и его используют 18 файлов.
Соседние роуты ведут себя правильно и на том же чужом `campaignId` отвечают отказом:

| Роут | Ответ | |
|---|---|---|
| `GET /api/campaigns/<чужой id>` | 404 `Campaign not found` | ✅ |
| `GET /api/campaign-content?campaignId=<чужой>` | 200, `data: []` (фильтр по `user_id`) | ✅ |
| `GET /api/proxy/trends?campaign_id=<чужой>` | 403 `Access denied` | ✅ |
| `GET /api/analytics/top-posts?campaignId=<чужой>` | 404 `CAMPAIGN_NOT_FOUND` | ✅ |

Течёт ровно три роута, которые хелпер не вызывают.

**Важный нюанс для фикса — дырка двухслойная.** `/api/keywords` и `/api/sources` ходят в
Directus **токеном самого пользователя**, и Directus эти строки отдаёт. Значит роль
`SMM Manager User` имеет право читать `campaign_content_sources` и `campaign_keywords`
целиком, без построчного ограничения. Поэтому фильтра в Express мало: нужно и починить роуты,
и урезать права роли в Directus, иначе тот же доступ останется через прямые запросы к Directus.
`/api/campaign-trends` — отдельный случай: он ходит **админским токеном**
([analytics.ts:318](../../server/routes/analytics.ts#L318)), там прав пользователя вообще нет
в уравнении, и защитить может только проверка в коде.

### F-2 (P2). `/api/campaign-trends` игнорирует `limit` и отдаёт 5.5 МБ

Проверено на проде — размер ответа не меняется вообще:

| `limit` | ответ |
|---|---|
| не задан | 5 586 512 Б, 1694 записи |
| `1` | 5 586 512 Б, 1694 записи |
| `5` | 5 586 512 Б, 1694 записи |
| `all` | 5 586 512 Б, 1694 записи |

Разбор задеплоенного бандла (`docker cp smm:/app/dist/server/index.js`) показывает, почему:
в проде у обработчика `const { campaignId } = req.query` — параметры `period` и `limit` не
читаются вовсе, а в Directus уходит захардкоженный `limit: -1` и `fields: "*"`.

Отдельно: `fields: "*"` тянет `raw_source_data` — полный сырой JSON исходного поста. Сервер
использует его только чтобы достать дату публикации (`extractPostDate`), после чего всё равно
отправляет клиенту целиком. Это и есть основная масса пятимегабайтного ответа.

**Осторожно, тут легко ошибиться в диагнозе** (я сам сначала ошибся): в рабочем дереве
`server/routes/analytics.ts` уже лежит незакоммиченная реализация с `limit`/`period`
(`DEFAULT_TRENDS_LIMIT = 500`, `MAX_TRENDS_LIMIT = 5000`, фильтр по `postDate`). Если читать
файл с диска, кажется, что всё починено. На проде этого кода нет — он не закоммичен.
Коммит `2500bf0ea perf(trends)` в истории есть, но он про клиентские фризы, а не про размер ответа.

### F-4 (P3). `GET /api/keywords/search` → 500 вместо 404

`search` и `analyze-website` — это POST-роуты ([ai.ts:423](../../server/routes/ai.ts#L423)).
GET по тем же путям проваливается в `app.get("/api/keywords/:campaignId")`
([campaigns.ts:371](../../server/routes/campaigns.ts#L371)) с `campaignId = "search"` и падает в
500 «Не удалось загрузить ключевые слова». Ожидается 404 или 405. Влияния на пользователей нет,
но 500 шумит в мониторинге и маскирует настоящие ошибки.

### F-5 (P2). Нестроковый `title` роняет создание и правку контента в 500

```bash
curl -s -X POST https://smm.omemo.tech/api/campaign-content \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"campaignId":"<свой id>","title":999,"content":"x"}'
```

→ `HTTP 500 {"error":"Failed to create content","details":"data.title.charAt is not a function"}`

То же с `"title":[1,2]`; `PATCH /api/campaign-content/:id` с `{"title":777}` → 500.
Причина — [content.ts:406](../../server/routes/content.ts#L406): `data.title.charAt(0)` вызывается
без проверки типа; тот же паттерн в PATCH и PUT. Ожидается 400 с валидационной ошибкой.
Побочно: поле `details` выносит наружу сырой текст JS-исключения.

### F-6 (P3). `GET /api/campaign-content/:id` → 500 вместо 404

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  https://smm.omemo.tech/api/campaign-content/00000000-0000-0000-0000-000000000000
```

→ `HTTP 500 {"error":"Failed to fetch content item"}`. Проверено мной лично, повторяется.
Причина — [content.ts:261](../../server/routes/content.ts#L261): общий `catch` превращает любую
ошибку Directus, включая 403 и 404, в 500. Данные при этом не утекают, страдает только код ответа.

### F-7 (P3). `/api/auth/me` отдаёт `unknown@email.com`

Проверено мной лично, два разных эндпоинта на одном и том же токене:

```
GET /api/auth/me       → {"email":"unknown@email.com","first_name":"","last_name":"", ...}
GET /api/user/profile  → {"email":"smmniap+claude-qa@gmail.com","first_name":"Claude", ...}
```

Причина — [auth-routes.ts:521](../../server/api/auth-routes.ts#L521): payload берётся base64-декодом
JWT **без проверки подписи**, а в токене логина полей `email`/`first_name` нет, поэтому
подставляется заглушка. Любой участок UI, берущий имя или почту из `/api/auth/me`, покажет
`unknown@email.com`.

Отдельно проговорю, потому что выглядит страшнее, чем есть: **это не обход авторизации.**
Боевые маршруты идут через `authenticateUser`, который валидирует токен апстримом в Directus
(`/users/me`), а `isAdmin` в этом же ответе считается отдельным авторитетным запросом
со static-токеном. Подделанный токен на защищённых маршрутах отклоняется. Проблема — только
в том, что отображаемые поля берутся из неверифицированного источника, где их попросту нет.

### F-8 (P2). У 340 из 845 «опубликованных» постов нет даты публикации

Прошёлся по всем 1422 записям контента владельца. Разбивка по статусам:

| статус | штук |
|---|---|
| `published` | 845 |
| `draft` | 427 |
| `partially_published` | 122 |
| `partial` | 22 |
| `error` | 3 |
| `scheduled` | 1 |
| `publishing` | 1 |
| `dreft` | 1 |

**У 340 записей со статусом `published` поле `published_at` пустое** — это 40% всех
опубликованных. Проверил не только режим сводки, но и полную форму записи через
`GET /api/campaign-content/:id`: там `published_at: null` тоже, то есть это не артефакт
маппинга, а реальное состояние базы.

Почему это важно именно сейчас: любой отчёт или график, который группирует по дате
публикации, эти 340 записей молча теряет. Под это подпадают «График активности за последние
30 дней» на дашборде и экспорт отчётов, который только что правили в `760ad1fed`. Цифра
«всего опубликовано» при этом верная — расходятся именно разрезы по времени.

Причину я не искал — это уже работа для разработчика. Вопрос в том, где теряется установка
`published_at` при публикации, и надо ли разово досчитать историю (например, из
`social_platforms` или из `date_updated`).

### F-10 (P2). `GET /api/campaign-content/:id` отдаёт форму, отличную от списка

Список ([content.ts:135](../../server/routes/content.ts#L135)) приводит запись к camelCase и
разбирает массивы через `parseArrayField`. Одиночный эндпоинт
([content.ts:457](../../server/routes/content.ts#L457)) отдаёт **сырую строку Directus как есть**:

```js
const response = await directusApi.get(`/items/campaign_content/${id}`, ...);
res.json({ data: response.data.data });   // без маппинга
```

Проверено на живой записи: в списке приходит `publishedAt`, по `:id` — `published_at`,
а `publishedAt` отсутствует. То же будет с `campaignId`/`campaign_id`, `imageUrl`/`image_url`
и с полями `keywords`/`hashtags`/`links`, которые в списке распарсены в массивы, а здесь
приедут строкой.

Отмечаю отдельно, потому что это прямо ломает предложенный план оптимизации страницы
«Контент»: там предлагалось дотягивать полный объект для диалога редактирования именно через
`GET /:id`. В нынешнем виде диалог получит поля не под теми именами. Эндпоинт надо сперва
привести к форме списка (и заодно починить F-6 — там же стоит общий `catch` в 500).

шаблон, что у `/api/sources` (нет `campaignId` → нет фильтра, `limit: 1000`).

### Почему фильтровать по `user_id` было нельзя

Ключевой вопрос оказался с неочевидным ответом. У `campaign_content_sources` колонка `user_id`
в схеме есть, но **её не пишет ни один путь создания** — ни `POST /api/sources`, ни
`trend-collector`, ни `telegram-channels-routes`, ни `autonomous-ai`. У `campaign_keywords`
такой колонки нет вовсе. Фильтр по `user_id` ночью опустошил бы владельцу списки источников
и ключевых слов. Принадлежность считается только через `user_campaigns`.

### Регрессия, которую поймал только прогон по проду

После первой выкатки фикса `GET /api/sources` и `GET /api/trends` стали отдавать **503**
любому неадмину — даже когда своя кампания у него есть. Тесты при этом были зелёные.

Причина: `listAccessibleCampaignIds` фильтровал по `_or[user_id, user_created]`, а живой
Directus отвергает это с 403 — «no permission to access field `user_created` in collection
`user_campaigns` or it does not exist». В SQL-схеме колонка есть, но у роли поля нет.
Fail-closed `catch` превращал 403 в 503.

Мок Directus такое поймать не мог в принципе, и тест дополнительно фиксировал именно
отвергаемую форму фильтра — то есть закреплял поломку. Исправлено в `f69783ec5`: фильтр
только по `user_id`, как в каноническом `GET /api/campaigns`; тест переписан.

**Вывод на будущее:** тесты с моком Directus проверяют форму запроса, а не то, что живой
Directus её примет. Для путей, где меняется фильтр или набор полей, нужен прогон по проду.

по одной коллекции с проверкой под аккаунтом владельца.

### F-12 (P3). Ссылка сброса пароля не одноразовая

[password-reset.ts:7](../../server/api/password-reset.ts#L7): токен — это чистый
`HMAC(userId:ts)`, серверного состояния нет. Отсюда следствия:

- **смена пароля не гасит ссылку** — она остаётся рабочей весь час;
- одной и той же ссылкой можно воспользоваться сколько угодно раз в пределах TTL.

Сценарий, где это стреляет: пользователь сбросил пароль, письмо осталось в почте (переслано,
общий ящик, утечка почты) — в течение часа по нему пароль меняется снова. Отраслевая норма —
одноразовый токен, гасящийся при использовании и при любой смене пароля.

Рядом, помельче, из того же файла:

- **сравнение токенов не константное по времени** ([:97](../../server/api/password-reset.ts#L97),
  обычный `!==`). Практически по сети эксплуатировать тяжело, но правильный ответ —
  `crypto.timingSafeEqual`;
- **захардкоженный запасной секрет** `'smm-reset-secret'`
  ([:8](../../server/api/password-reset.ts#L8)). Сейчас не стреляет: если админского токена нет,
  подтверждение всё равно упадёт в 500 раньше. Но это мина — при другом порядке проверок
  публичная строка из репозитория становится ключом подписи токенов сброса;
- **пользователю не приходит письмо о том, что пароль сменили** — то есть чужой сброс проходит незаметно.

### Проверено, и здесь всё в порядке

- **Инъекция через заголовок `Host` не проходит.** `getBaseUrl`
  ([:12](../../server/api/password-reset.ts#L12)) строит ссылку сброса из `req.get('host')` —
  это классический вектор увода токена: подставил свой Host, письмо ушло настоящему
  пользователю, а ссылка в нём ведёт на домен атакующего. **Но не эксплуатируется:** traefik
  маршрутизирует по домену и отдаёт 404 на любой чужой Host (проверил с `evil.replit.dev` и
  `attacker.roboflow.space`). Подмена через `X-Forwarded-Host` тоже не работает: код читает
  именно `req.get('host')`, который в Express возвращает сырой заголовок и на `trust proxy`
  не реагирует.

  Записываю как скрытый риск, а не как дыру: защищает инфраструктура, а не код. Стоит выкинуть
  вычисление базового URL из заголовка и брать его из переменной окружения.
- **Существование аккаунта не раскрывается** — на несуществующий email тот же `{"success":true}`.
- **Валидация подтверждения сброса держит мусор:** пустое тело, подделанный токен, короткий
  пароль, протухший и будущий `ts`, `userId` объектом, пароль числом — везде 400 с внятным
  текстом, ни одной 500.
- Сброс и регистрация под `sensitiveLimiter` (20 попыток за 15 минут).

## 8. Четвёртый заход: даты публикации, одноразовый сброс, 405

Выкачено `f807964ed`, `814516471`, `a549dfb46` (плюс параллельные `1611c6dbd`, `d183979fc`).
Точка отката — образ `root-smm:rollback-before-2012`.

### F-8: причина найдена, история досчитана НЕ будет

Корень — в [shared/schedule-time.ts](../../shared/schedule-time.ts): `isConfirmedPublishedPlatform`
считает платформу опубликованной по `postId`/`postUrl` **даже без** `publishedAt`, а
`getContentAggregateTimes` собирает дату **только** из `publishedAt`. То есть если n8n записал
платформу с `postUrl`, но без даты, статус контента становится `published`, а дата остаётся пустой.
В publish-now дыра была закрыта хелпером `resolvePublishFinalization`, остальные пути его не звали.

Три пути записи, все чинились:

1. `publish-scheduler.ts` — основной по объёму, шёл мимо хелпера;
2. `publishing-routes.ts` (`mark-as-published`) — статус писался через storage, а дата отдельным
   запросом под токеном **случайной активной сессии**; нет сессий → токен `null` → дата не ставилась,
   ошибка глушилась;
3. `social-platform-status-webhook.ts` — подстраховочный PATCH слал camelCase `publishedAt`,
   которого в таблице нет, из-за чего Directus отбивал **весь** запрос и статус не обновлялся вовсе.

**Историю решено не досчитывать, и я с этим согласен.** Восстановить дату можно только там, где
хотя бы одна платформа в `social_platforms` несёт свой `publishedAt`. Где не несёт ни одна —
честного источника нет: `date_updated` это время любой последней правки (редактирование текста,
пересчёт статуса, миграция), и подстановка нарисовала бы в графике активности ложные всплески
в дни, когда ничего не публиковалось. Молчаливый пропуск лучше правдоподобной выдумки.

Скрипт `scripts/maintenance/backfill-published-at.ts` положен, **на проде не запускался**.
По умолчанию dry-run, запись только по `--apply`, трогает исключительно восстановимую часть.

### F-12: ссылка сброса стала одноразовой

Гасится при использовании (до обращения к Directus, поэтому повтор не доходит до смены пароля),
при любой смене пароля — включая смену из профиля, — и при выдаче новой ссылки. Добавлены
`crypto.timingSafeEqual`, письмо-уведомление о смене пароля; убран запасной секрет
`'smm-reset-secret'`.

**Компромисс, о котором надо знать:** хранилище — `Map` в памяти процесса. Рестарт контейнера
гасит все выданные ссылки, и пользователю придётся запросить письмо заново. Это fail-closed
(рестарт ссылку гасит, а не воскрешает), но при деплое в момент, когда кто-то сбрасывает
пароль, он увидит «недействительная ссылка». При нескольких инстансах ссылка будет валидна
только на выдавшем — сейчас инстанс один.

Отдельно проверил после выкатки, что удаление запасного секрета ничего не сломало: запрос
сброса и на несуществующий, и на реальный адрес отвечает 200 без ошибок в логе, то есть путь
подписи токена и отправки письма отработал. `timingSafeEqual` не падает на токенах разной длины
(1, 8 и 40 символов — везде 400).

### F-4: 405 вместо 500

`GET`, `DELETE`, `PUT` на `/api/keywords/search` и `/api/keywords/analyze-website` теперь дают
**405** с заголовком `Allow: POST`. Настоящие идентификаторы кампаний обслуживаются как прежде
(чужой → 404 от проверки доступа).

### Мутационная проверка — важная деталь

Возврат `!==` вместо `crypto.timingSafeEqual` **мутацию сначала пережил**: постоянство времени
поведением не отличимо, обычный тест его не ловит. Добавлен структурный тест, оборачивающий
реальный `crypto.timingSafeEqual`. Это стоит запомнить: у защиты от тайминга нет наблюдаемого
поведения, и проверять её надо иначе, чем остальную логику.

Тестов стало **1260** (было 1161), 114 файлов. `npm run check` чист.
В легаси-конфиге 457 ошибок против 455 ночью — это +2 того же класса
(«Property does not exist on type `{}`» на нетипизированных ответах Directus) в

## 9. Риск захвата админского аккаунта через утраченный почтовый ящик

Владелец сообщил, что **не имеет доступа к почте, на которую заведён его основной админский
аккаунт**: ящик использовался командой и остался у человека, который из команды ушёл.

### Почему это горит

Восстановление пароля отправляет ссылку на почту аккаунта. Значит тот, у кого остался доступ
к ящику, **в любой момент забирает админский аккаунт**: запрашивает сброс, получает письмо,
задаёт свой пароль. Дальше у него права `is_smm_admin` — то есть доступ к списку всех 97
пользователей, к их тарифам и срокам, и к админским эндпоинтам. Механизм сброса, который
я этой ночью укреплял (одноразовая ссылка, `timingSafeEqual`, уведомление о смене), работает
корректно — и ровно поэтому он честно отработает на владельца ящика.

Обратная сторона: **владелец сам не может воспользоваться восстановлением пароля** для своего
основного аккаунта.

### Хорошая новость: чинится из интерфейса, без Directus

`PUT /api/user/profile` ([user.ts:74](../../server/routes/user.ts#L74)) передаёт новый `email`
в Directus. То есть почту аккаунта можно сменить на подконтрольную прямо со страницы профиля.

Админка дополнительно умеет `PATCH /admin/users/:userId`
([admin-users.ts:120](../../server/routes/admin-users.ts#L120)) с полями `is_smm_admin`,
`status`, `plan`, `expire_date` — то есть снять админские права и перевести аккаунт
в `suspended`. Смены чужой почты там нет.

**Никаких действий с аккаунтами я не предпринимал** — это решение владельца, и ошибиться тут
дорого.

### F-14 (P2). Смена почты и пароля в профиле не требует подтверждения

Найдено при разборе предыдущего пункта, в том же обработчике
[user.ts:74](../../server/routes/user.ts#L74):

- **новый пароль применяется без ввода текущего** — в теле запроса достаточно `new_password`;
- **новая почта применяется без подтверждения по ссылке** — смена мгновенная.

Следствие: одного украденного токена сессии достаточно, чтобы полностью забрать аккаунт —
поменять пароль, не зная старого, и переписать почту на свою, после чего законный владелец
теряет и вход, и возможность восстановления. Уведомление о смене пароля, добавленное ночью,
уйдёт уже на новый адрес, если атакующий сменит почту первой.

Что надо: запрашивать текущий пароль при смене пароля и почты, а новую почту подтверждать
ссылкой, оставляя старую активной до подтверждения. Уведомление о смене адреса слать на
**старый** адрес.

Отдельно замечу по общей картине: из 97 пользователей **все 97 в статусе `active`**, ни один
не деактивирован. Процесса отключения ушедших людей, судя по этому, нет вовсе.
