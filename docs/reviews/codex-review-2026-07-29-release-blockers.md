## Находки

### P1 — cross-tenant отмена публикации через storage fallback

Файлы и строки:

- `server/api/publishing-routes.ts:1002-1091`
- `server/storage.ts:107-123`
- `server/storage.ts:882-977`
- `server/storage.ts:1083-1200`

`getCampaignContentById(id, authToken)` после отказа пользовательского токена
не завершает чтение, а перебирает `tokenCache` всех пользователей. При
настроенном `DIRECTUS_SERVICE_TOKEN` `getAuthToken(userId)` возвращает этот
служебный токен для произвольного пользователя.

`POST /api/publish/cancel/:contentId` сначала делает прямой PATCH с токеном
запросившего пользователя, но затем безусловно вызывает
`storage.updateCampaignContent(contentId, updates)` без токена. Storage
повторно находит владельца чужой записи и выполняет PATCH служебным токеном.

Конкретный сценарий:

1. Залогиненный пользователь получает UUID чужого scheduled content.
2. Его токен получает 403 на Directus GET.
3. Storage fallback читает запись служебным токеном.
4. Прямой PATCH токеном атакующего не проходит.
5. Fallback-update переводит чужую запись в `draft`, очищает `scheduledAt` и
   `socialPlatforms`.

Дополнительные последствия:

- `publishing-routes.ts:1023` кеширует токен атакующего под `userId` владельца;
- `GET /api/publish/status/:contentId` на строках 967-990 через тот же fallback
  раскрывает статус, расписание и платформы чужой записи.

Тест `server/__tests__/retry-and-clone.test.ts:81-99` мокает storage успешным и
не моделирует отказ пользовательского токена с последующей эскалацией.

Ожидаемый инвариант: отказ чтения пользовательским токеном является
окончательным для пользовательского маршрута. Служебный доступ должен быть
отдельным явным API и вызываться только после `assertContentBelongsToRequester`.

### P1 — проверяется своя кампания, но admin-действие идёт по чужому trendId

Файл и строки:

- `server/api/trends-routes.ts:1164-1207`
- `server/api/trends-routes.ts:1217-1257`
- `server/api/trends-routes.ts:1802-1915`

В трёх ручках `ensureTrendsCampaignAccess` проверяет `campaignId` из тела, но
последующий admin-запрос фильтрует только по независимому `trendId`/`trendIds`:

- `/api/trends/collect-comments`;
- `/api/trends/collect-comments-single`;
- `/api/analyze-comments`.

Конкретный сценарий: атакующий передаёт ID своей кампании и ID чужого тренда.
Проверка кампании проходит, после чего:

- внешний scraper получает задачу по чужому тренду;
- `analyze-comments` читает чужие комментарии и записывает анализ в чужой
  `campaign_trend_topics`;
- при `level=source` определяется и изменяется чужой
  `campaign_content_sources`.

Все операции выполняются с `useAdminToken: true`, поэтому Directus tenant
boundary здесь не участвует.

Ожидаемый инвариант: объект, над которым выполняется действие, должен быть
загружен сервером; его фактическая `campaign_id` должна быть авторизована.
Независимая пара `campaignId + trendId` от клиента не является доказательством
связи.

### P1 — ambiguous payment reservation освобождается orphan-reclaimer

Файлы и строки:

- `server/routes/yookassa.ts:97-140`
- `server/routes/yookassa.ts:199-210`
- `server/services/promo-reservation.ts:120-133`
- `server/services/promo-reservation.ts:253-271`

После сбоя `attachPaymentId` код пытается отменить платёж. Если отмена вернула
не `canceled`, упала или платёж уже перешёл в `succeeded`, бронь правильно
остаётся `reserved` и помечается `needs_reconciliation`.

Но `isSlotHolderDead` считает любую бронь без `yookassa_payment_id` старше
30 минут брошенной, не проверяя `needs_reconciliation`. Следующий вызов
`reservePromo` запускает `reclaimDeadReservations`, который выбирает все
`reserved` строки и освобождает такую бронь.

Конкретный сценарий:

1. YooKassa создала платёж, Directus не сохранил его ID.
2. Отмена не подтверждена; платёж мог успеть стать `succeeded`.
3. Через 30 минут новый покупатель запускает reclaim и получает освободившийся
   слот скидки.
4. Поздний webhook первого платежа видит `released` и не выдаёт подписку.

Итог: у первого клиента списаны деньги без подписки, а слот скидки переиспользован.

Дополнительно `flagReservationReconciliation` не проверяет `res.ok`: Directus
PATCH 500 логируется как успешная постановка на сверку.

Ожидаемый инвариант: бронь с известным внешним платежом или
`needs_reconciliation=true` никогда не освобождается по возрасту. YooKassa ID
должен сохраняться вместе с reconciliation-маркером, а ошибку записи маркера
нельзя принимать за успех.

### P2 — свежий occupiedSlots перечёркивается локальной stale-пометкой

Файл: `server/services/promo-reservation.ts:374-400`.

После unique conflict код перечитывает фактические занятые слоты, а затем
безусловно выполняет `occupied.add(slot)`.

Сценарий при `max_uses=1`: A занимает слот 0 и освобождает его до перечитывания
B. B получает пустой свежий `occupied`, снова локально добавляет слот 0 и на
следующей итерации отвечает `exhausted`, хотя код свободен.

После `occupied = await occupiedSlots(promoId)` дополнительный `add` не нужен:
если слот занят, он уже есть в результате.

### P2 — SM-9 не закрыл все локальные границы календарного дня

Файлы и строки:

- `client/src/components/PublicationCalendar.tsx:212-314,438`
- `client/src/pages/dashboard/index.tsx:193-205`
- `client/src/pages/posts/index.tsx:175-193`

Публикация `29.07 01:00 МСК` хранится как `28.07 22:00Z`. В браузере с `TZ=UTC`
календарь продолжает сравнивать даты через локальные `startOfDay/isSameDay`, а
метрики «сегодня» и «эта неделя» — через локальные `isToday/isThisWeek`.
Подпись и график уже московские, но календарь и счётчики могут положить запись
в предыдущий день.

`posts/index.tsx` также создаёт `new Date(dateString)` напрямую и обходит
нормализацию строк Directus без `Z`, добавленную в `date-utils`.

Фиксированный `Europe/Moscow` соответствует текущему серверному контракту
ввода. Хранение timezone у кампании — отдельная продуктовая миграция, а не
условие закрытия SM-9.

### P3 — скрытый потолок конкурентности безлимитного промокода

Файл: `server/services/promo-reservation.ts:41-50,306-308`.

`UNLIMITED_SLOT_ATTEMPTS = 200`. При 201 синхронном покупателе последний может
проиграть гонку за слоты 0-199 и получить ошибку, хотя слот 200 свободен.
Текущий тест проверяет 50 параллельных запросов.

Для ограниченного промокода бюджет `max_uses + 100` пропорционален ёмкости.
Проблема относится к фиксированному пределу кода без `max_uses` и усиливается
stale-пометкой из предыдущей находки.

## Что подтверждено как корректное

- Исключение `/api/video-temp/:uuid` точное и method-aware: только `GET/HEAD`.
  Кодирование `..`, двойные и хвостовые слэши не совпадают с регуляркой;
  заголовок подмены метода не обрабатывается; `POST` получает 401.
- CAS в `transitionReservation` отличает HTTP-сбой Directus от проигрыша гонки:
  не-2xx бросает ошибку, 2xx с пустым массивом означает, что условие уже не
  выполнилось.
- `finalizePromoRedemption` не зацикливается и повторно подписку не выдаёт.
- Основные publish handlers больше не принимают клиентский объект `content` за
  источник истины.
